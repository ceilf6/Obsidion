# 底层

所以假如我想看JS底层，最好是去看JS的源码而不是V8的源码？因为V8可能会和ES规范不一致？

这个问题要分目的来看：

---

## 取决于你想理解什么

| 目的 | 应该看什么 |
| --- | --- |
| **理解 JS 语言语义**（作用域、this、原型链等的"是什么"） | ECMAScript 规范 [tc39.es/ecma262](https://tc39.es/ecma262/) |
| **理解 JS 实际运行行为**（"为什么这段代码跑得快/慢"） | V8 源码 |
| **理解某个 quirk 的原因**（如 `typeof null === "object"`） | 规范 + 引擎历史 |

---

## V8 和规范的关系不是"不一致"

V8 并不是"不遵守规范"，而是：

1. **规范描述的是语义（what），V8 实现的是机制（how）**
    
    规范用"LexicalEnvironment + VariableEnvironment 两条链"描述 `var` 和 `let` 的区别，V8 用"同一条 Context 链 + `VariableMode` 标记"来达到**相同的可观测行为**，但实现路径更高效。你在 JS 层永远看不出差异。
    
2. **规范有意留出实现自由度**
    
    规范定义的是**抽象操作**，不规定内存布局。V8 的 `NativeContext`、`ScopeInfo`、`Context slot` 都是实现细节，没有对应的规范概念。
    
3. **真正不一致的情况极少且是 bug**
    
    V8 的 bug tracker 里确实有"spec compliance"类 bug，但这是需要修复的异常，不是常态。
    

---

## 实践建议

```
想搞清楚"JS 应该怎么工作" → 看规范
想搞清楚"JS 实际怎么执行" → 看 V8
两者结合才能真正理解      → 先规范建立心智模型，再 V8 验证实现细节
```

比如你之前问的执行上下文：

- **规范** 告诉你"有 LexicalEnvironment、VariableEnvironment、ThisBinding 这三个概念"
- **V8** 告诉你"这三个概念最终被压缩成 `Context` 对象 + `VariableMode` 枚举，`this` 大多数情况根本不进 Context"

单看规范你会误以为运行时真的有两条链；单看 V8 你会搞不懂为什么 `kVar` 和 `kLet` 要区别对待。**两者互相印证才完整**。

## Babel 和 V8

```css
JSX / ESNext
        ↓
     Babel
        ↓
   普通JS代码，例如 React.createElement
        ↓
      V8
   (Ignition → TurboFan)
        ↓
      机器码
```

Babel 将代码转换为 普通JS 交给 V8 执行
