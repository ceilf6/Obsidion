# 银行家算法过程例子

# **8. 一个完整例子**

下面给你一个经典的小例子。

设有 3 类资源：

- `A`
- `B`
- `C`

总资源为：

```
Total = [10, 5, 7]
```

当前系统状态：

## **8.1 Alloc 矩阵**

```
        A  B  C
P0      0  1  0
P1      2  0  0
P2      3  0  2
P3      2  1  1
P4      0  0  2
```

## **8.2 Max 矩阵**

```
        A  B  C
P0      7  5  3
P1      3  2  2
P2      9  0  2
P3      2  2  2
P4      4  3  3
```

---

## **8.3 Need = Max - Alloc**

```
        A  B  C
P0      7  4  3
P1      1  2  2
P2      6  0  0
P3      0  1  1
P4      4  3  1
```

---

## **8.4 Available**

先算当前已分配总量：

- A: `0+2+3+2+0 = 7`
- B: `1+0+0+1+0 = 2`
- C: `0+0+2+1+2 = 5`

所以：

```
Available = Total - Alloc总和
          = [10,5,7] - [7,2,5]
          = [3,3,2]
```

---

# **9. 用安全性算法检查**

初始：

```
Work = [3,3,2]
```

看谁满足 `Need <= Work`

---

## **第一步**

### **P1**

`Need[P1] = [1,2,2] <= [3,3,2]`
可以完成

完成后释放它持有的资源 `Alloc[P1] = [2,0,0]`

```
Work = [3,3,2] + [2,0,0] = [5,3,2]
```

安全序列目前：

```
<P1>
```

---

## **第二步**

### **P3**

`Need[P3] = [0,1,1] <= [5,3,2]`
可以完成

释放 `Alloc[P3] = [2,1,1]`

```
Work = [5,3,2] + [2,1,1] = [7,4,3]
```

安全序列：

```
<P1, P3>
```

---

## **第三步**

### **P4**

`Need[P4] = [4,3,1] <= [7,4,3]`
可以完成

释放 `Alloc[P4] = [0,0,2]`

```
Work = [7,4,3] + [0,0,2] = [7,4,5]
```

安全序列：

```
<P1, P3, P4>
```

---

## **第四步**

### **P0**

`Need[P0] = [7,4,3] <= [7,4,5]`
可以完成

释放 `Alloc[P0] = [0,1,0]`

```
Work = [7,4,5] + [0,1,0] = [7,5,5]
```

安全序列：

```
<P1, P3, P4, P0>
```

---

## **第五步**

### **P2**

`Need[P2] = [6,0,0] <= [7,5,5]`
可以完成

释放 `Alloc[P2] = [3,0,2]`

```
Work = [7,5,5] + [3,0,2] = [10,5,7]
```

所有进程都完成。

所以该状态**安全**。
一个安全序列是：

```
<P1, P3, P4, P0, P2>
```

# **10. 图示理解**

可以把它画成一种“资源逐步回流”的过程。

初始空闲资源：

```
Available = [3,3,2]
```

---

## **10.1 第一个能完成的进程**

```
Work=[3,3,2]
      ↓
   发现 P1 的 Need=[1,2,2] 可满足
      ↓
   让 P1 完成
      ↓
   P1 释放 Alloc=[2,0,0]
      ↓
Work=[5,3,2]
```

---

## **10.2 第二个能完成的进程**

```
Work=[5,3,2]
      ↓
   P3 的 Need=[0,1,1] 可满足
      ↓
   P3 完成并释放 [2,1,1]
      ↓
Work=[7,4,3]
```

---

## **10.3 后续**

```
Work=[7,4,3]  -> P4 完成 -> Work=[7,4,5]
Work=[7,4,5]  -> P0 完成 -> Work=[7,5,5]
Work=[7,5,5]  -> P2 完成 -> Work=[10,5,7]
```

---

# **11. 一个“请求要被拒绝”的例子**

还是上面这个系统。

假设 `P1` 现在提出请求：

```
Request[P1] = [1,0,2]
```

先检查：

### **是否超过 Need？**

`Need[P1] = [1,2,2]`
所以 `[1,0,2] <= [1,2,2]`，合法

### **是否超过 Available？**

`Available = [3,3,2]`
所以 `[1,0,2] <= [3,3,2]`，当前够分

于是进入试探分配。

---

## **11.1 试探分配后**

### **新 Available**

```
[3,3,2] - [1,0,2] = [2,3,0]
```

### **新 Alloc[P1]**

```
[2,0,0] + [1,0,2] = [3,0,2]
```

### **新 Need[P1]**

```
[1,2,2] - [1,0,2] = [0,2,0]
```

---

## **11.2 再做安全性检查**

初始：

```
Work = [2,3,0]
```

检查谁能完成：

- `P1 Need=[0,2,0]` 可以
- 完成后释放 `Alloc[P1]=[3,0,2]`
- `Work=[5,3,2]`

后面就还能继续找到其他进程

所以这次请求可以批准。

---

# **12. 为什么它有效**

因为它不是只看“当前资源够不够”，而是看：

分配后，系统是否仍然保留“至少一条让大家都能活下去”的路。

所以它避免了那种情况：

- 当前看似可以分
- 但分完后所有进程都卡住
- 互相等资源
- 最终进入死锁

---

# **13. 它和图归纳的关系**

你前面问的图归纳，本质上和安全性检查非常接近。

可以对应起来看：

| **图归纳** | **银行家算法** |
| --- | --- |
| 找可归纳进程 | 找 `Need <= Work` 的进程 |
| 删除进程结点 | 标记 `Finish[i]=true` |
| 删除占有边并释放资源 | `Work = Work + Alloc[i]` |
| 最终删光全部结点 | 所有进程都 `Finish=true` |
| 删不动了 | 不安全 |

所以你可以把**安全性算法**理解成：

把“资源分配图的归纳思想”改写成矩阵和向量计算

---

# **14. 银行家算法的优点**

### **优点**

- 能在运行过程中动态分配资源
- 能避免系统进入不安全状态
- 理论上能有效避免死锁

---

# **15. 银行家算法的缺点**

### **缺点很重要，考试常问**

### **1. 必须预先知道最大需求**

每个进程必须事先声明 `Max`

但现实中很多程序做不到准确声明。

---

### **2. 算法开销较大**

每次资源请求都可能要试探分配 + 安全性检查

进程多、资源类多时开销不小。

---

### **3. 资源数通常假定固定**

系统中的总资源量通常认为是确定不变的

现实环境可能更复杂。

---

### **4. 可能导致进程长期等待**

虽然避免了死锁，但某些请求可能一直被拒绝，从而产生饥饿现象。

# **16. 你这段定义里一个小补充**

你写的是：

- `Alloc`
- `Req`
- `A`
- `E`

这套写法可以用，但更标准、更常见的是：

- `Max`
- `Alloc`
- `Need = Max - Alloc`
- `Available`
- `Total`

因为如果只有 `Req/Need`，你能做安全性判断；

但若要做“资源请求算法”的完整合法性检查，还需要知道最大声明需求 `Max`。

---

# **17. 一句话总结**

银行家算法的核心就是：

**每次分配资源前，先假设分配，再检查系统是否仍存在安全序列；若存在则分配，否则拒绝。**

---

# **18. 考试/做题时的固定步骤**

你可以按这个模板做题：

### **已知矩阵后：**

1. 先算 `Need = Max - Alloc`
2. 先算 `Available = Total - 各列Alloc之和`
3. 令 `Work = Available`
4. 找满足 `Need <= Work` 的进程
5. 找到后执行 `Work += Alloc`
6. 记录安全序列
7. 重复直到全部完成或卡住
8. 全部完成则安全，否则不安全

### **如果还有请求：**

1. 检查 `Request <= Need`
2. 检查 `Request <= Available`
3. 试探分配
4. 做安全性检查
5. 安全则批准，不安全则回滚
