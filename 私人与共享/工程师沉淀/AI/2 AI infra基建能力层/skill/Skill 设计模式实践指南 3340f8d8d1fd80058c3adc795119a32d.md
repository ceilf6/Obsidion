# Skill 设计模式实践指南

> **摘要**：Google Cloud 于 2026 年初通过 Agent Development Kit（ADK）正式发布了 5 种 Agent Skill 设计模式。这不只是一套编写规范——而是一套将 AI Agent 从"玩具"变成"生产工具"的工程方法论。本文深入解析每种模式的原理、量化效果和实践方式。
> 

---

### 背景：Prompt 工程进入结构化时代

### 单一巨型 Prompt 的失败

过去一年，大量工程师尝试用 AI 自动化业务流程，最终碰壁的原因几乎都一样：**Prompt 膨胀**。
刚开始写 10 行 Prompt 效果不错，然后加需求、加约束、加示例……到最后一个 Agent 的系统 Prompt 动辄 3000 字，问题随之而来：
- LLM 注意力分散，开始忽略后半段指令
- 每次修改一处，其他地方莫名其妙出错
- 不同场景下行为完全不可预测
- 根本无法 debug：出了问题不知道改哪里
这不是 Prompt 写得不够好的问题，是**结构性问题**。LLM 的上下文窗口是有限的，注意力是分散的，越长越密的 Prompt，遗漏关键规则的概率越高。

### [SKILL.md](http://skill.md/) ：从容器到架构

2025 年 12 月，Anthropic 联合 Google、Microsoft 等在 [agentskills.io](http://agentskills.io/) 发布了 Agent Skill 开放标准，规范了 [SKILL.md](http://skill.md/) 文件格式。Google Cloud ADK、Claude Code、Gemini CLI、OpenClaw、VS Code Copilot 等 30+ 工具迅速采用这一格式。
但 [SKILL.md](http://skill.md/) 的**格式**问题很快就解决了。2026 年初，真正的战场转移到了**内容设计**：一个 Skill 内部，指令应该怎么组织？
Google Cloud Tech 官方 X 账号（2026 年 3 月）整理了生产级 Agent 系统中最常见的 **5 种内容设计模式**：

| 模式 | 中文名 | 解决的核心问题 |
| --- | --- | --- |
| Tool Wrapper | 工具包装器 | 专有 API/库规范的上下文污染 |
| Generator | 生成器 | 多次执行输出结构不一致 |
| Reviewer | 评审器 | 评审规则臃肿、难以维护 |
| Inversion | 控制反转 | 基于猜测而非事实的规划 |
| Pipeline | 流水线 | 复杂任务跳步、丢步问题 |
| **量化数据**：在 ADK 相关任务上，合理应用这些设计模式后，代码正确率从 **29% 提升到 99%**（+245%）。架构正确性评分从 4 分跳到 9 分（满分 10），反模式规避从 2 分到 9 分。来自 arXiv 的研究表明，生产系统每个 Skill 平均使用 **2 种模式的组合**。 |  |  |

### [SKILL.md](http://skill.md/) 基础结构速览

在深入模式之前，先了解 [SKILL.md](http://skill.md/) 的三层加载机制（Progressive Disclosure）：

```
skill-name/
├── SKILL.md          # 必须：元数据 + 核心指令（< 500 行）
├── references/       # 可选：详细参考资料，按需加载
│   ├── conventions.md
│   └── review-checklist.md
├── assets/           # 可选：模板、配置文件、数据
│   └── report-template.md
└── scripts/          # 可选：可执行脚本
    └── validate.py
```

**三层加载策略（节省 Token 的核心）**：
- **L1 Metadata（~100 tokens/skill）**：每次会话启动时，**所有** Skill 的 `name` 和 `description` 都会加载，用于 Agent 判断是否激活某个 Skill
- **L2 Instructions（建议 < 5000 tokens）**：Skill 被触发时，加载完整 [SKILL.md](http://skill.md/) 正文
- **L3 Resources（按需加载，无上限）**：references/ 和 assets/ 中的文件只在 Agent 执行时需要才读取
实际含义：**安装 50 个 Skill 的常驻上下文成本 ≈ 5000 tokens**，与安装 1 个几乎一样。庞大的知识库可以放在 L3，完全不影响日常开销。

### 5 种设计模式详解

### 模式一：Tool Wrapper（工具包装器）

### 解决的问题

当 Agent 需要和多种不同技术栈交互时（比如：FastAPI、SQLAlchemy、各类 CLI 工具），如果把每种技术的使用规范都塞进系统 Prompt，会导致：
- 上下文溢出，Agent 行为变"泛"
- 调 FastAPI 时把其他 CLI 工具的规范也带进来，产生干扰
- 规范更新时要改系统 Prompt，影响全局
**核心机制**：把某种技术的使用规范打包成一个独立 Skill，**只在需要时激活**。关键文件是 `references/conventions.md`，它是可替换的知识载体：换一个文件，同一套 Skill 逻辑就能服务完全不同的技术栈。

### [SKILL.md](http://skill.md/) 示例

```yaml
---
name: fastapi-expert
description: FastAPI 专家模式，提供符合 FastAPI 最佳实践的代码生成和审查。
  当用户需要编写、审查或调试 FastAPI 代码、或说"写个API接口"时使用。
---

# FastAPI Expert Skill

激活后，立即读取 `references/conventions.md` 了解团队的 FastAPI 规范。

## 生成代码时
- 严格遵循 Annotated 依赖注入风格
- 所有参数必须包含类型注解
- 遵循 references/conventions.md 中的命名规范

## 审查代码时
- 逐项检查 references/conventions.md 中的规则
- 对每个违规点，说明违反了哪条规则并给出修正建议
- 只报告 conventions.md 中明确定义的违规，不凭感觉评判
```

```markdown
<!-- references/conventions.md（可替换，不影响 Skill 主体逻辑）-->
# FastAPI 团队规范 v2.1

## 依赖注入
- 使用 Annotated 风格：`user: Annotated[User, Depends(get_current_user)]`
- 禁止直接在函数签名中调用 Depends()

## 路由规范
- 路由函数命名：动词 + 名词（如 get_user, create_order）
- 必须包含 response_model 和 status_code
- 路径参数使用下划线命名
```

### 用 vs 不用的差异

| 维度 | 不用 Tool Wrapper | 用 Tool Wrapper |
| --- | --- | --- |
| 上下文使用 | 全部技术规范常驻，浪费 2000+ tokens/规范 | 按需加载，空闲时 0 cost |
| 代码准确率 | ~60%（多规范混用时互相干扰） | ~95%（专注当前技术栈） |
| 维护成本 | 修改一处可能影响全局行为 | 每个 references/*.md 独立维护 |
| 扩展能力 | 添加新技术需修改系统 Prompt | 新建一个 Skill 目录即可 |
| **适用场景**：框架专家（FastAPI、Django、ADK）、CLI 工具封装（各类内部/外部 CLI）、代码库规范（SQL 规范、代码风格指南）。 |  |  |

### 模式二：Generator（生成器）

### 解决的问题

数据报告、PRD 文档、事故复盘……这类内容有个共同特点：**你知道该有什么章节，但每次生成的格式都不一样**，导致：
- 下游自动化程序解析报告时频繁失败（章节名不统一）
- Leader 收到的报告风格五花八门
- "上次你帮我写的格式比这次好"——Agent 根本不记得上次的结构
**核心机制**：Skill 不直接包含模板内容，而是协调两个文件：
- `assets/template.md`：输出的结构骨架（必须有哪些章节、格式）
- `references/style-guide.md`：填充内容的规范约束（语气、字数、示例）
Agent 的角色从"直接输出"变成"项目经理"：收集必要变量 → 对照规范 → 填充模板 → 保证所有章节都存在。

### [SKILL.md](http://skill.md/) 示例

```yaml
---
name: incident-report-generator
description: 生成标准化的数据事故报告。当用户需要写数据事故报告、
  故障复盘文档、数据异常说明时使用。
---

# 数据事故报告生成器

## 执行步骤

### Step 1：读取资源
- 读取 `assets/incident-template.md` 了解报告的必须章节
- 读取 `references/style-guide.md` 了解写作风格要求

### Step 2：收集必要信息
**在开始生成报告前，必须先收集以下所有信息。缺少任何一项都不得生成报告。**
逐一询问（每次只问一个问题）：
- [ ] 事故发生时间和持续时长
- [ ] 受影响的表 / 指标 / 业务线
- [ ] 根因（已确认或待确认的说法均可）
- [ ] 已采取的修复措施

### Step 3：生成报告
所有信息收集完毕后，严格按照 `assets/incident-template.md` 的结构填充报告。
**必须保留模板中所有章节，即使某些章节暂时没有内容，也要写"待补充"。**

## 输出
最终输出一个完整的 Markdown 文档，含 template 中定义的全部章节。
```

```markdown
<!-- assets/incident-template.md -->
# 数据事故报告

## 基本信息
| 项目 | 内容 |
|------|------|
| 事故时间 | {start_time} ~ {end_time} |
| 影响范围 | {affected_scope} |
| 严重级别 | P0 / P1 / P2 |
| 发现方式 | 监控告警 / 用户反馈 / 巡检发现 |

## 问题描述
{problem_description}

## 根因分析
{root_cause}

## 修复措施
{fix_actions}

## 时间线
{timeline}

## 预防机制
{prevention}
```

### 用 vs 不用的差异

不用 Generator 时：
- 第 1 次生成的报告有"根因分析"章节
- 第 2 次没有这个章节
- 下游 Slack 机器人解析报告失败
- 同事抱怨"这个格式和上次不一样"
用 Generator 后：**100% 的执行都会产出结构完全相同的文档**，可以直接接入自动化处理流程。
**适用场景**：事故复盘、周报月报、API 文档、Commit Message 规范化、PRD 模板生成。

### 模式三：Reviewer（评审器）

### 解决的问题

传统的"代码审查 Skill"通常把所有评审规则都写在 [SKILL.md](http://skill.md/) 里，随着规则增加，文件越来越长，最终变成和之前一样的"大 Prompt"。更糟的是，当你想把"Python 审查"改成"安全审查"，整个 [SKILL.md](http://skill.md/) 都要重写。
Reviewer 模式的突破在于：**把"如何审查"（流程）和"审查什么"（标准）分离**。
**核心机制**：
- `SKILL.md`：定义审查流程（如何审查、如何汇报结果、输出格式）
- `references/review-checklist.md`：定义审查标准（审查什么，可随时替换）
只需替换 `checklist` 文件，同一套 Skill 即可执行：Python PEP8 审查、SQL 性能审查、数据安全合规审查、OWASP 安全审查。

### [SKILL.md](http://skill.md/) 示例

```yaml
---
name: sql-code-reviewer
description: SQL 代码质量和规范审查。当用户需要审查 SQL 质量、
  检查 SQL 是否符合规范、排查 SQL 性能问题时使用。
---

# SQL 代码审查 Skill

## 执行协议

1. 读取 `references/review-checklist.md` 获取本次审查的检查项列表
2. 逐行阅读并理解用户提交的 SQL，建立对逻辑的完整理解
3. 逐条遍历 checklist，判断每一项是否违规
4. 按照下方格式输出审查报告

## 输出格式（严格遵守，不得省略任何章节）
```

### SQL 审查报告

**总体评分：X/10**
发现问题：X 个（🔴 严重：X | 🟡 警告：X | 🔵 提示：X）

---

### 🔴 严重问题（必须在提交前修复）

```
- **[行 X]** {问题描述}
	- 违反规则：{checklist 中的规则名}
	- 修改建议：`{改后的代码片段}`
```

### 🟡 警告（强烈建议修复）

...

### 🔵 提示（可选优化）

...

---

### Top 3 改进建议

1. 
    - ...
2. 
    - ...
3. 
    - ...

```

```

```markdown
<!-- references/review-checklist.md（随时可替换，不影响 Skill 主体）-->
# Hive SQL 审查 Checklist v1.2

## P0：严重规则（必须遵守）
- [ ] 禁止 SELECT *，必须明确列出字段
- [ ] WHERE 条件必须包含分区字段（否则全表扫描）
- [ ] JOIN 条件必须使用等值连接，禁止笛卡尔积
- [ ] 不得直接查询含 PII 字段的表（字段名含 phone/id_card/name）

## P1：性能规则（强烈建议）
- [ ] 大表 JOIN 时，小表放在右侧（Hive MapJoin 优化）
- [ ] 避免在 WHERE 子句对字段做函数转换（影响分区裁剪）
- [ ] GROUP BY 字段数量不超过 5 个（超出考虑拆分）

## P2：规范规则（建议遵守）
- [ ] 表名和字段名使用蛇形命名（snake_case）
- [ ] SQL 开头有注释说明业务目的和作者
- [ ] 子查询层数不超过 3 层（超出考虑用 WITH 子句）
```

### 量化效果

Reddit 社区引用的案例：将 `review-checklist.md` 替换为 ADK 代码治理规范后，代码质量评分从 **29% 跳到 99%**（Giorgio Crivellari 的 ADK 治理 Skill 实测，2026 年 2 月）。核心原因：**显式的 checklist 颗粒度，远超"请帮我检查代码质量"这样的模糊指令**。LLM 对明确的检查项清单遵守率接近 100%，对模糊指令的遵守率只有 40-60%。
**适用场景**：PR 代码审查、SQL 质量检查、数据报告合规审核、架构设计 Review、发布前 Checklist。

### 模式四：Inversion（控制反转）

### 解决的问题

大多数 Agent 的默认行为是：用户说 → Agent 立即做。但当任务依赖大量上下文时，Agent 往往会**基于假设而非事实开始执行**，产出一个"看起来专业但充满错误假设"的结果，最终需要多轮修改。
Inversion（控制反转）模式颠覆了这个交互方式：**Agent 先提问，用户先回答，信息足够后 Agent 再开始执行**。控制权从用户转移到了 Agent。
**核心机制**：在 [SKILL.md](http://skill.md/) 中设置**显式的门控指令（Gating Instructions）**——用强制性语言严格规定 Agent 在没有收集到必要信息之前，绝对不能开始执行任务。
关键细节：门控指令必须使用**不容妥协的绝对语言**（"禁止"、"绝对不能"、"必须等到"），而不是建议性语言（"建议先收集"）。LLM 对绝对指令的服从率远高于模糊指令。

### [SKILL.md](http://skill.md/) 示例

```yaml
---
name: etl-task-designer
description: 设计数据 ETL 任务方案。当用户需要设计新的数据处理任务、
  规划数据管道架构、说"帮我设计个ETL"时使用。
---

# ETL 任务设计 Skill

**⚠️ 铁律：在完成所有 Phase 的信息收集之前，禁止输出任何方案内容。**
**即使用户催促"你直接给我个方案就行"，也不得跳过信息收集阶段。**

---

## Phase 1：业务理解

依次询问以下问题，**每次只问一个**，等待回答后再问下一个：

1. "这个任务要解决什么业务问题？最终使用者是谁？"
2. "产出数据的消费场景是什么？（看板 / API / 下游任务 / 报表）"
3. "数据更新频率要求是什么？（T+1 / 实时 / 按需触发）"

✋ **Phase 1 完成检查**：以上 3 个问题均已得到明确回答后，才能进入 Phase 2。

---

## Phase 2：技术约束

**注意：Phase 1 未完成前，禁止开始 Phase 2 的提问。**

1. "源数据在哪里？（Hive 表名 / API 地址 / 文件路径）"
2. "有没有现有的上游任务可以依赖？"
3. "有哪些不可违反的技术约束？（如：禁止 Full Scan 大表 / 只能用特定队列）"

✋ **Phase 2 完成检查**：以上问题均已得到明确回答后，才能进入 Phase 3。

---

## Phase 3：方案输出

**Phase 1 + Phase 2 均完成后才执行本阶段。**

读取 `assets/etl-design-template.md`，基于收集到的真实信息填充方案文档。
主动标注哪些地方仍有不确定性，并列出需要用户进一步确认的问题。
```

### 用 vs 不用的差异

| 场景 | 不用 Inversion | 用 Inversion |
| --- | --- | --- |
| 用户说"帮我设计一个数据 ETL" | Agent 立即产出一套充满假设的方案，需要多轮修改（平均 4-6 轮） | Agent 先提问，基于真实约束产出方案，修改轮次减少约 70% |
| 方案质量 | 结构合理但细节大量偏差 | 与实际需求高度吻合，通常 1-2 轮即可定稿 |
| 用户体验 | 感觉 AI 在"猜" | 感觉 AI 在"理解你" |
| **适用场景**：ETL 任务设计、项目规划、需求文档生成、数据治理方案制定、任何"输入模糊、输出有严格要求"的场景。 |  |  |

### 模式五：Pipeline（流水线）

### 解决的问题

对于复杂的多步骤任务，LLM 有一个顽固的习性：**压缩中间步骤，直奔最终结果**。你让它"分析数据 → 制定方案 → 编写代码 → 测试验证"，它极可能直接给出代码，把前两步变成内心活动而非可见输出。
ADK 官方数据：在不使用 Pipeline 模式的情况下，Agent 在"多步骤 SQL 生成+验证"任务中**跳步率高达 73%**。
Pipeline 模式的解法：**把工作流程本身写进指令，每个步骤都是一个显式的检查点，必须产出可见成果并获得用户确认，才能推进到下一步**。
**核心机制**：
- 步骤顺序固化在 [SKILL.md](http://skill.md/) 中，不可跳过
- 每步骤末尾设置"钻石门控"（Diamond Gate）：要求用户确认后才继续
- 每步骤只加载该步骤需要的资源文件，上下文保持整洁
使用 Pipeline 后，完整流程执行率从 27% 提升到 **97%**。

### [SKILL.md](http://skill.md/) 示例

```yaml
---
name: km-article-pipeline
description: 学城文章生产全流程（调研 → 写作 → 审查 → 发布）。
  当用户需要写学城文章、技术博客、知识沉淀文档时使用。
---

# 学城文章生产流水线

本 Skill 按严格顺序执行 4 个 Stage，每个 Stage 完成后必须等待用户确认才能继续。
**禁止跳过任何 Stage，禁止合并执行多个 Stage。**

---

## 📋 Stage 1：调研与大纲

**执行内容：**
1. 理解用户的文章主题和目标读者
2. 使用 web_search 进行多轮搜索（至少 3 组关键词）
3. 产出文章大纲，包含每章节的核心论点

**输出格式：**
```

### 文章大纲

```
- 标题：[建议标题]
- 目标读者：[角色描述]
- 预计字数：[XXX 字]
```

### 章节规划

### 组合使用：1+1 > 2 的进阶技巧

5 种模式并非互斥，而是**可组合、可嵌套**的。Google Cloud Tech 官方推荐的组合逻辑：

> "A Pipeline skill can include a Reviewer step at the end to double-check its own work. A Generator can rely on Inversion at the very beginning to gather the necessary variables before filling out its template."
—— Google Cloud Tech 官方 X（2026-03）
> 

### 组合选择矩阵

| 问题场景 | 主模式 | 推荐组合 | 收益 |
| --- | --- | --- | --- |
| 专业技术领域 + 需要质量保证 | Tool Wrapper | + Reviewer | 规范遵守 + 质量把关 |
| 结构化文档输出 + 输入信息不足 | Generator | + Inversion | 先采集再生成，100% 结构一致 |
| 复杂多步骤流程 + 中间质量门 | Pipeline | + Reviewer | 流程完整 + 每步都有质量保证 |
| 任务规划 + 信息完整再输出 | Inversion | + Generator | 采集完整信息后生成规范文档 |

### 深度案例：Pipeline + Reviewer（多阶段任务开发）

典型场景：需求理解 → SQL/代码编写 → 质量审查 → 提交。

```yaml
---
name: sql-dev-pipeline
description: SQL 开发全流程（需求理解 → SQL编写 → 质量审查 → 提交）。
  当用户需要开发数仓SQL、说"帮我写个SQL"并涉及多个步骤时使用。
---

# SQL 开发流水线

## Stage 1：需求理解（Inversion 子模式）
**禁止在收集完以下信息前开始写 SQL：**
1. 目标：这个 SQL 要计算什么指标？2. 数据来源：依赖哪些 Hive 表？
3. 时间范围：计算哪个时间周期的数据？

✅ Stage 1 完成，等待确认后进入 Stage 2。

## Stage 2：SQL 编写（Generator 子模式）
1. 读取 `references/sql-standards.md` 了解 SQL 规范
2. 读取 `assets/sql-template.md` 获取 SQL 结构骨架
3. 按模板编写初版 SQL，使用 SELECT 先做逻辑验证

✅ Stage 2 完成，等待确认后进入 Stage 3。

## Stage 3：SQL 质量审查（Reviewer 子模式）
1. 读取 `references/sql-review-checklist.md`
2. 按 checklist 逐条审查 Stage 2 生成的 SQL
3. **所有 P0 问题必须修复后才能进入 Stage 4**
4. 输出审查报告和修复后的 SQL

✅ Stage 3 完成，等待确认后进入 Stage 4。

## Stage 4：提交
1. 将最终 SQL 写入 `{task_name}.sql` 文件
2. 如需要，创建任务草稿（仅草稿，不上线）
3. 提示用户：上线操作需要人工确认
```

这个 Skill 组合了 **Inversion（Stage 1）+ Generator（Stage 2）+ Reviewer（Stage 3）+ Pipeline（整体框架）**，4 种模式协同，覆盖了从模糊需求到高质量 SQL 的完整路径。

### 快速选型指南

面对一个新 Skill 的设计需求，用以下决策树选择模式：

```
你的 Skill 主要做什么？
│
├─ 封装某个特定工具/API/框架的使用规范
│  └─ 用 Tool Wrapper
│     （如果还需要质量检查：Tool Wrapper + Reviewer）
│
├─ 生成结构化文档/报告/代码
│  ├─ 输入信息经常不足？ → Generator + Inversion
│  └─ 输入信息通常充足？ → 单独 Generator
│
├─ 对已有内容做评审/检查
│  └─ 用 Reviewer
│     （如果审查标准会变：把 checklist 放进 references/）
│
├─ 需要在执行前先采集信息
│  └─ 用 Inversion
│     （采集完后生成文档：Inversion + Generator）
│
└─ 复杂的多步骤任务，每步都要可见成果
   └─ 用 Pipeline
      （需要中间质量门：Pipeline + Reviewer）
```

### 总结

### 核心思想的三句话

1. 
    - **从"大 Prompt"到"模块化 Skill"**：把知识和规则拆散到 references/ 和 assets/，[SKILL.md](http://skill.md/) 只负责协调流程，不存储具体内容。
2. 
    - **用设计模式解决结构性问题**：跳步用 Pipeline 解决，输出不一致用 Generator 解决，假设驱动用 Inversion 解决，规则臃肿用 Reviewer 解决，上下文污染用 Tool Wrapper 解决。
3. 
    - **模式可组合，按需叠加**：生产系统平均每个 Skill 使用 2 种模式，最常见组合是 Pipeline + Reviewer 和 Generator + Inversion。

### 上手路径建议

建议按以下顺序实践：
**Week 1**：选一个现有 Skill，在其中加入 Inversion 门控，解决"模糊输入"问题。成本极低，只需改 [SKILL.md](http://skill.md/) 开头几行。
**Week 2**：为一个高频生成任务（如周报、事故报告）创建 Generator Skill，把模板提取到 assets/，效果立竿见影。
**Week 3**：把 SQL 审查规则整理成 checklist，用 Reviewer 模式替换原来的模糊审查指令，代码质量分立刻上涨。
**Month 2**：选一个完整的多步骤工作流，用 Pipeline 模式将其标准化，每步设置检查点。
