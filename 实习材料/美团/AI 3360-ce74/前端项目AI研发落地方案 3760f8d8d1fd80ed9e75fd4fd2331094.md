### 一、背景

当前前端项目覆盖C/B/M端业务场景（端侧()多、技术栈()多），团队已在不同场景下结合AI探索相关研发范式，同时结合[到餐产研AI交付新范式](https://km.sankuai.com/collabpage/2746299325?from=citadel_collabpage)推进落地3类模式（Claw、Vibe、AI-SDLC）试点。为保障各场景聚焦和多角色可介入，特此同步一下相关方案、实操以及认知对齐，方便后续协力做工。

### 二、实施方案

### **2.1 交付流程全景**

> 研发交付并非孤立的编码过程，而是研发、产品、QA 深度协同的全链路体系，从需求评审、技术方案设计、AI Coding，到集成/UI 测试与运维，每个阶段环环相扣。
AI-SDLC（AI-Driven Software Development Life Cycle）的目标是从需求到发布的周期，提升端到端效能。依托 **AI-Ready PRD**、**AI-Ready 仓库**、**SDD 研发流程**、**质量保障**，以 AI 驱动各阶段工具与方法的协同升级，实现端到端交付效率提升。
简化为 5 个阶段：**需求澄清** -> **方案设计** -> **编码开发** -> **测试验收** -> **上线观测**。每个阶段只保留核心交付和质量门禁。
| 阶段 | 核心交付 | 质量门禁 |
| --- | --- | --- |
| 需求澄清 | PRD / 设计稿 / 验收标准 | 范围清晰，验收可判定 |
| 方案设计 | 技术方案 / Spec / 任务拆解 | 方案可执行，任务可拆解 |
| 编码开发 | Repo / 代码变更 | 单测与 CR 通过，风险可回滚 |
| 测试验收 | 冒烟 / 联调 / 验收报告 | 阻断问题清零，产设验收通过 |
| 上线观测 | 灰度 / 监控 / 反馈闭环 | 指标稳定，问题闭环 |
>

2.

###### 第一步：BrainStorming 阶段

| 1. 投喂物料（PRD、接口文档、当前代码库等） | 2. 方案讨论 | 3. 生成 OpenSpec 范式 初版文档 |
| --- | --- | --- |
|  |  | 主要生成 proposal、design、spec、task 文档 |
###### 第二步：打磨文档

从技术和业务角度拆解PRD，可以先生成一份传统前端技术方案作为辅助，逐步打磨完善相关文档。其中，specs 文档建议按 Capabilities 功能维度拆解，方便后续 Tasks 文档、Plan 文档以模块化形式执行。
```markdown
openspec/changes/order-floating-layer-12/
  ├── .openspec.yaml
  │   └── OpenSpec change 元信息，声明该变更使用 spec-driven schema 和创建日期。
  ├── README.md
  │   └── 变更简介，说明本 change 是“点单浮层 1.2”需求。
  ├── proposal.md
  │   └── 提案文档，描述为什么要做、改什么、影响哪些能力和模块。
  ├── design.md
  │   └── 技术设计文档，描述基于当前仓库代码的实现方案、关键决策、风险和迁移计划。
  ├── specs/
  │   └── order-floating-layer-12/
  │       └── spec.md
  │           └── 能力规格文档，用 OpenSpec Requirement/Scenario 形式定义系统必须满足的行为。可以按照 Capabilities 功能维度拆分
  └── tasks.md
      └── 实施任务清单，把实现拆成类型、策略、默认选择、展示、购物车兼容、验证等可勾选步骤。
```

### 第三步：生成 plan 文档

根据 OpenSpec 相关文档，执行 superpowers 工具，生成 plan 文档

### 第四步：出码

按照 plan 文档，选择「superpowers:subagent-driven-development」或「superpowers:executing-plans」模型出码。如有需求或代码变动，按需循环执行第2~4步。

### 第五步：归档

完成开发&验证后，执行 OpenSpec 归档，需求沉淀为“数字资产”。

<details>
<summary>踩过的坑</summary>

- *Step 7 自检查反馈弱：**深度还原流程里的 Step 7 视觉验证能够发现一些差异，但反馈弱、效果差，不能完全依赖它自动完成闭环。实际使用时仍需要研发人工对照设计图和本地页面，判断哪些差异必须修、哪些可以接受。
**图片滥用：**AI 有时会把本应由组件、文字、CSS 样式实现的区域处理成图片，导致页面可维护性变差，也不利于后续接入真实数据和交互。Review 时需要重点检查页面是否存在不合理的图片化实现。
**依赖高质量设计图：**Forge 对设计图质量比较敏感。更理想的设计图需要嵌套结构合理、分层有序，组件边界清晰。如果设计图图层混乱、层级不清或大量元素合并，Forge 生成的中间产物质量会下降，后续样式和结构修正成本会增加。

</details>

<details>
<summary>使用心得</summary>

Forge 适合承担页面开发中的基础还原工作，人更适合负责质量判断和业务取舍。比较合理的分工是：Forge 负责结构、组件、样式和基础交互；研发负责识别图片滥用、修正视觉细节、补齐业务字段和接口逻辑。

</details>
