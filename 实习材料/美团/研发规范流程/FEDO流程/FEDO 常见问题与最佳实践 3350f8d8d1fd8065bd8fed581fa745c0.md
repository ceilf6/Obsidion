写在最前：当前阶段各技术栈流程存在一定差异性，例如 MRN/容器化 与 WEB 在分支处理流程上存在不同，但整体具备相似性。本篇最佳实践以 WEB 类型切入，涉及部分其他技术栈内容。
名词解释
迭代：默认情况下，一次迭代对应一个需求的交付过程。不同技术栈在迭代维度有一定的调整，例如 MRN 迭代可以对应一个 Native 版本或一个发版周期。
任务：对应一个需求下的任务，一个任务可以由开发和发布组成，一个任务对应一个项目、一个 Ones 任务。
项目：一次需求交付过程中，开发和发布的所围绕的实体，例如 WEB 侧对应的 Talos 项目、MRN 侧对应为 Bundle（单仓库多 Bundle 场景下，每个 Bundle 是一个独立的项目）、小程序侧对应 Talos 项目、Native 对应 APP 组件。

## 1）迭代任务

1. 
    - 一个需求涉及到一个项目的改动，开发和部署的流程是怎样的？
    一个需求创建一个迭代，创建对应项目的开发任务和部署任务，完成项目的开发和部署
2. 
    - 一个需求涉及多个 WEB 项目的改动，开发流程、部署流程是怎样的？
    WEB 侧当前场景最佳实践：一个需求创建一个迭代，包含所有的开发和部署任务。
3. 
    - 开发流程：不同项目创建各自的开发任务，产出各自待上线的 release 分支；
4. 
    - 部署流程：不同项目各自走单项目部署，部署工作流之间互不影响；（存在多项目需要串并行发布的场景，可以使用协同交付能力）
5. 
    - 多人参与的开发流程如何整合？
    多人参与场景类似于“一个需求多个项目”，以需求为维度划分为不同的迭代，同一个迭代内的开发任务可以各自走单项目部署，也可以各个开发任务<u>集成至同一个 release 分支同时灰度</u>（目前集成至同一分支流程建设中，过渡期可在“创建发布分支”节点关联同一个 release 分支）；

## 2）工作流

1. 
    - Bugfix工作流、Hotfix工作流在哪些场景会用到？
2. 
    - 现阶段 WEB 与 MRN 场景存在一定差异。以 WEB 举例，通常情况下，Bugfix 工作流用作 “PM/QA 验收失败，需要关联 Ones 缺陷并修复问题、重发测试环境”、“灰度放量前，验收有问题需要修复 release 分支场景（建设中）”。
    一般场景习惯上直接在 feature 分支上修改 bug，并重发测试环境。所以目前在“ PM/QA 验收”节点**可选**的启动 Bugfix 流程。
3. 
    - Hotfix 流程一般用于快速上线。针对前端场景，默认 Hotfix 流程同样需要走灰度，但不限制放量时间，所以目前 Hotfix 流程在创建完 Hotfix 分支后，集成至 release 分支进行灰度
    与常规开发部署流程相比较，Hotfix 工作流在开发环境去掉了个别不需要的节点，同时 Hotfix 工作流**不上报度量信息**。
4. 
    - 在 Hotfix 紧急发版的情况下，一般没有 Ones 任务，或者有的开发没有 Ones 任务怎么办？
    目前开发任务不作区分统一需要录入 Ones，短期方案可以跟 PM 讨论下提供一个默认 Hotfix 需求，下面拆分同学自己的 Hotfix 任务用于无开发任务的发版
    后续 FEDO 会提供 Hotfix 类型工作流无需关联 Ones，同时长期方案（讨论中）针对没有 Ones 的开发任务提供一个默认的Ones 可关联项，省去手动创建，同时有度量数据

注：如果暂时没有可用的 Ones，同时需要快速发版修复线上问题，可以线下完成 hotfix 开发并合并到 release 这一步，在 FEDO 上直接启动部署工作流（需要挂载至某个迭代下）
3. - FEDO 侧推荐使用 Hotfix 工作流还是直接使用无开发任务部署处理快速发版？
这两种目前都支持。FEDO 的建议是使用 Hotfix 工作流开发，可以完成团队流程线上化，后续 FEDO 和业务团队可以持续优化现有的研发流程
4. - 协同发布支持什么能力？
目前协同发布在 WEB 场景下开发使用，用于存在串并行发布场景，例如某些存在先后顺序的发布，或者多个 WEB 项目并行发布
文档见[https://km.sankuai.com/page/1350951710](https://km.sankuai.com/page/1350951710)
（建设中）针对多个 WEB 项目并行发布场景，协同发布支持多个项目一键审批、一键灰度、一键放量与全量，减少多项目发布场景的重复操作。

## 3）度量相关

1. 
    - 前端项目的指标衡量是以MDO数据为主，还是FEDO数据为主 ？具体两者之间的关系是什么？
2. 
    - 前端项目度量数据以 MDO 数据为准。前端的项目的度量数据由 FEDO 产生，并上报到 MDO，MDO 侧统一展示前后端的度量数据，即 FEDO 为 MDO 提供大前端范围的度量底层数据；
3. 
    - 前端项目的指标衡量，例如需求交付周期是通过节点打点计算，是不是说明某些节点在开发流程中是必须要的？
4. 
    - 是的，FEDO 工作流中的度量上报、卡控等节点是必须的，FEDO 会锁定上报等关键节点，团队规范基于基础工作流定制；
5. 
    - FEDO 上报的 MDO 度量度量点都有哪些？
6. 
    - 开始开发时间
7. 
    - 指标口径：用户在开发分支相对于主分支的首次提交 commit 时间
8. 
    - 上报时机：FEDO 分支关联 Ones 需求后
9. 
    - PR 创建时间
10. 
    - 指标口径：用户在 FEDO 创建 Feature-> Release PR 的时间点
11. 
    - 上报时机：FEDO PR 创建节点运行成功后
12. 
    - PR 合并时间
13. 
    - 指标口径：用户在 FEDO 操作 Feature -> Release 合并的时间点
14. 
    - 上报时机：FEDO PR 合并节点运行成功后
15. 
    - 开始发布&发布完成
16. 
    - 指标口径：用户在 FEDO 完成全量发布的时间的时间点
17. 
    - 上报时机：全量节点发布后

## 4）Ones 篇

目前标准工作流都内置了哪些 Ones 节点或 Ones 能力？

1. 
    - Ones 状态流转：用于将原来手动流转的 Ones 任务替换为插件执行，自动调整 Ones 状态；
2. 
    - 分支关联 Ones 工作项：将当前开发分支绑定至当前 Ones 任务所在的 Ones 需求，用于上报度量信息；
3. 
    - （可选）Ones 提测节点：完成创建提测任务，并卡控提测任务的状态；

## 5）分支流程

1. 
    - 基于 FEDO 的分支流是怎样的？
    FEDO 基于[https://km.sankuai.com/page/143886652](https://km.sankuai.com/page/143886652)规范，默认整合了标准化分支流程：
2. 
    - 开发时创建 feature 分支，完成开发、测试、验收过程中的迭代；
3. 
    - 开发完成的 feature 分支向 release 分支发起 PR，完成 code review 后合并至 release/xx；
4. 
    - （待线上化）灰度的 release/xx 分支在灰度验收环节需要修复时，通过 release/xx 切出 bugfix 分支或直接在 feature 分支（此时 release 分支未集成其他 feature 代码）完成修复重提 PR，合并后执行灰度热更新验证；
5. 
    - 灰度期间存在线上环境变化时，由 release/xx 同步 master 分支执行热更新；
6. 
    - 灰度结束后，将 release 分支合并至 master 分支；
7. 
    - release 分支同步 master 分支时存在冲突怎么办？
    release 分支同步 master 冲突时，复用当前 feature 分支同步最新代码解冲突，完成后通过 PR 合入 release 分支

## 6）灰度篇

1. 
    - 灰度发布的分支落后于主分支怎么办？
    在灰度前，我们可以通过“最新代码检查”节点检查当前部署分支是否同步了主分支
2. 
    - 灰度期间同项目有人发布线上环境该如何处理？
    FEDO 会在项目灰度策略变更、全量上线等操作前，默认检查当前分支与主分支是否存在差异，如果有则默认开启灰度热更新工作流
3. 
    - 灰度结束后 release 需要合并至 master 总是会忘记怎么办？会不会有遗漏风险？
    现状：当存在 release 未合并至 master 的工作流，目前会在灰度启动时进行强提示，用于检查当前
    正在补充优化：
4. 
    - 存在灰度结束未合并至 master 的情况，提醒工作流未完成；
5. 
    - 存在 release 至 master 分支未合并情况强制卡控其他灰度操作；
6. 
    - 简化 release 至 master CR 流程；

## 7）回滚流程

WEB 项目的回滚流程是怎样的？
目前回滚工作流正在建设中，包含回滚、周知等关键节点，同时可以一键启动。
过渡期可以直接使用“线上版本管理”模块完成研发组项目回滚，与原 Talos 流程一致

## 8）与其他平台的关联

1. 
    - FEDO 目标是一站式管理，那么 Ones 的填写，MDO 的需求状态的查询等等 ，后续怎么操作？
    FEDO 定位大前端 DevOps，前端研发链路中涉及到的**高频**平台流转、规范执行等都计划在工作流或平台模块中一站式整合。短期可能存在部分未线上化的流程需要补充（例如需要跳出站点填写提测工单、MDO 查看度量数据），长期会作为 FEDO 节点或模块整合，降低效率损耗。
2. 
    - 非业务系统，如技术项目，npm包之类的，后续如何进行发布？
    Q4 预期关闭 Talos 线上发布入口，后续会逐渐将 Talos 能力整合至 FEDO，目前 NPM 包支持直接通过 FEDO 发布，技术项目如果没有灰度能力、或者使用云函数等 FEDO 暂不支持的技术栈，可以先走加白，后续迁移至 FEDO
3. 
    - 如果使用 FEDO 进行线上发布，那么节点中部署环节的发布链接用户还能点击并访问吗？
    不影响。FEDO 会渐进式整合 Talos 现有的能力，例如部署后的发布链接是系统的发布地址，会以更清晰的方式周知/展示给发布及相关同学。

2. 
    - 检查构建流水线add-mtistanbul插件日志，其中有插装前后babel文件的对比。不影响构建正式包
3. 
    - FEDO是否有非平台人工操作研发任务和工作流能力，如对外暴露的openapi， 或者mcp、skills等？
4. 
    - 欢迎使用[0968168675](https://friday.sankuai.com/mcp/skill-detail?activeTab=overview&from=/skills-market?deepseek=false%26keyword=fedo%26orderByDownloadCount=all%26orderByTotalCallCount=all%26orderByTotalCallerCount=all%26page=1%26pageSize=30%26tag=%26verifiedType=all%26viewMode=card%26visibility=all&id=2764)
5. 
    - 自测覆盖率节点失败
6. 
    - [https://km.sankuai.com/collabpage/2167208929](https://km.sankuai.com/collabpage/2167208929)[https://km.sankuai.com/collabpage/1328506053](https://km.sankuai.com/collabpage/1328506053) 大多数覆盖率相关问题都可以通过删除报告重新上传覆盖率报告来解决
7. 
    - FEDO中mrn构建测试包节点，对于三端发布中鸿蒙端发布一直卡在MRN-Build是为什么？
8. 
    - 需要检查下babel.config.js配置中：是否存在 @gfe/babel-plugin-react-add-name
    因为该插件没有适配鸿蒙，会导致用FEDO构建测试包时卡死在MRN-BUILD节点，解决方法：babel.config.js配置中删除当前插件
9. 
    - 发布MRNbundle时某几个包触发发布失败
10. 
    - 排查发布失败的bundle再触发灰度发布时是否存在正在进行中的发布任务（如未审批的白名单发布）
11. 
    - 是否一次性发布大量bundle（bundle*app数大于100）会导致dd接口超限，联系FEDO同学提升dd接口限额
12. 
    - 能否修改项目技术栈
13. 
    - 不能，需要重新导入项目
14. 
    - MRN信息录入时，想要配置的版本下届置灰无法选择
15. 
    - [https://fedo.sankuai.com/self-service/unlock-mrn](https://fedo.sankuai.com/self-service/unlock-mrn)自助手动解锁卡控后重试节点。
16. 
    - [ones提测节点](https://fedo.sankuai.com/node/detail/469)失败
17. 
    - 检查流水线前面的分支绑定ones节点是否成功。如果失败大多数是因为1:流水线绑定的ones不是子需求、2两个不同需求复用了分支。
18. 
    - 问题1解决方案： 如果必须提测的话，终止本开发任务，使用子需求类型的ones重新创建任务
19. 
    - 问题2解决方案：在ones中，手动操作，将开发分支绑定到本开发任务的子需求的父需求上
20. 
    - DUO模板/节点相关问题，直接拉节点维护人来排查，我们不负责维护
21. 
    - mrn/max 项目中构建Node版本问题，如果发现构建流水线中yarn/pnpm相关节点无法正常执行，提示错误是node版本相关问题，那应该怎么修改node版本？
22. 
    - 可以在项目信息中直接修改【构建Node版本】进行选择
23. 
    - 如果选择跟随模版，则需要查看使用工作流模版中构建相关节点，进行配置构建Node版本或者使用自定义镜像功能
24. 
    - Web项目灰度发布期间，操作放量是提示的发布结果观测是什么？应该怎么使用？
25. 
    - [https://km.sankuai.com/collabpage/1946090609](https://km.sankuai.com/collabpage/1946090609)
26. 
    - 在研发组中新增MAX/MRN导入项目为什么无法找到bundle？
27. 
    - 添加的仓库地址和分支是否正确；
28. 
    - 该分支下是否存在max.config.js文件；
29. 
    - 一个项目只能在一个研发组下，需确保项目未在其他研发组下存在。
30. 
    - 解决方案：确认分支和配置文件存在，或将项目迁移到正确的研发组下。
