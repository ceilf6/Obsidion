# codex分析

这两个仓库本质上都不是“组件库”，而是 Duo 的“页面协议/页面编排仓库”。

可以把它们和你现在看的几个仓库这样理解：

- `ka-mop-max-duo`
作用：组件库。里面是 `@meishi/ka-mop-shop-cart`、`@meishi/ka-mop-shop-cart-modify` 这些可复用组件。
- `food-cart`
作用：购物车页面的协议仓库。负责定义“购物车页要请求什么、怎么组装、页面上摆哪些组件、组件事件怎么串起来”。
- `duo-food-order-submit`
作用：提单/提交订单页的协议仓库。负责定义“提单页怎么请求预下单数据、怎么组装秒提/团购/优惠/支付前置这些模块”。
- `duo-page`
作用：通用运行壳。把协议仓库生成成真正可运行的页面代码，再在 `.duo-tmp/preview-xxxx` 里启动。

**`food-cart` 是干什么的**

`food-cart` 里现在这个页面是 `mop-cart-list`，从 [pageBuildConfig.json](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/pageBuildConfig.json) 就能看出来：

- `baseUrl` 是 `https://rpc.meituan.com/grouptrade/cartpage/`
- `pageUrl.h5` 是 `food-mop-cart-list`
- `pageQuery` 需要 `poiId`、`brandId`

所以它对应的是“购物车页”，不是提单页。

更关键的是它直接依赖了你现在看的这些购物车组件，见 [componentsMap.json](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/componentsMap.json)：

- `@meishi/ka-mop-shop-cart`
- `@meishi/ka-mop-shop-cart-bottom`
- `@meishi/ka-mop-shop-cart-title`
- `@meishi/ka-mop-shop-cart-modify`

它还在 [dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/dataSourceMap.groovy) 里定义了购物车页的请求参数和动作类型，比如：

- `10` 查询购物车
- `11` 查询购物车规格详情
- `40` 修改商品规格

在 [struct.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/struct.groovy) 里则把页面结构拼出来，比如：

- `MopShopCartList`
- `CartBottomBar`
- `MeishiKaMopShopCartModify`

所以 `food-cart` 更像“购物车页面本身的 Duo 页面源码”。

**`duo-food-order-submit` 是干什么的**

这个仓库对应的是“提交订单/提单页”，从 [pageBuildConfig.json](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/pageBuildConfig.json) 就很明显：

- `baseUrl` 是 `https://rpc.meituan.com/grouptrade/precreate/`
- `pageUrl.h5` 是 `food-order-submit`
- MRN 页名是 `GroupOrderSubmit`

它依赖的模块也明显偏提单页，见 [componentsMap.json](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/componentsMap.json)：

- `@meishi/submit-miaoti-container`
- `@meishi/group-buy-tab`
- `@meishi/food-group-submit-logic`
- 还有 `@meishi/ka-mop-deal-card-list`、门店确认弹窗等

在 [struct.groovy](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/struct.groovy) 里能看到：

- `CartGroupDealList`
- `MopContainer`
- `MopDataContainer`

在 [dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/dataSourceMap.groovy) 里还能看到它会把购物车相关信息带进提单请求：

- `cartParam`
- `productList`
- `promoParamMap`

所以它不是“购物车页”，而是“从商品/购物车进入后的提单页协议源码”。

**它们和 `duo-page` 的关系**

你可以理解成：

1. `food-cart` / `duo-food-order-submit`
负责写页面协议源文件：
- `struct.groovy`
- `dataSourceMap.groovy`
- `constData.groovy`
- `componentsMap.json`
- `pageBuildConfig.json`
1. `duo-page`
负责把这些协议源编译/生成成真正可运行的页面代码
2. `ka-mop-max-duo`
提供页面里要用到的业务组件包

所以如果你现在想追“购物车页的数据到底在哪里定义请求”，优先看：

- [food-cart/mop-cart-list/dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/dataSourceMap.groovy)

如果你想追“提单页的数据怎么把购物车/秒提数据带进去”，优先看：

- [duo-food-order-submit/dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/dataSourceMap.groovy)

`ka-mop-max-duo` 组件 -> `food-cart` 协议 -> `duo-page` 运行页

你这个纠正是对的，我刚才把“源码”说得太笼统了。

更准确地说，这里有 3 层“源码”：

1. 组件实现源码
    
    在 [ka-mop-shop-cart](https://www.notion.so/Users/ceilf6/Desktop/ka-mop-max-duo/packages/ka-mop-shop-cart/src/index.tsx) 和 [ka-mop-shop-cart-modify](https://www.notion.so/Users/ceilf6/Desktop/ka-mop-max-duo/packages/ka-mop-shop-cart-modify/src/index.tsx) 这种 `packages/*/src` 里。
    
    这里写的是组件本体怎么渲染、怎么响应点击、怎么组装回调参数。
    
2. 页面协议/数据编排源码
    
    在 [food-cart/mop-cart-list/struct.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/struct.groovy)、[food-cart/mop-cart-list/dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/dataSourceMap.groovy)、[duo-food-order-submit/struct.groovy](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/struct.groovy)、[duo-food-order-submit/dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/duo-food-order-submit/dataSourceMap.groovy) 里。
    
    这里写的是页面怎么请求、请求参数怎么拼、把哪些字段传给哪个组件、组件事件怎么回流到页面请求。
    
3. 运行时代码
    
    在 `duo-page/.duo-tmp/...` 里。
    
    这是前两层被编译/生成之后的可运行页面，不是你平时主要维护的业务源码入口。
    

所以不是说 `food-cart` 和 `duo-food-order-submit` “才是组件源码”，而是：

- 组件源码在 `ka-mop-max-duo/packages`
- 页面级数据流源码在 `food-cart` / `duo-food-order-submit`

拿你关心的购物车举例：

- 购物车组件本体在 [ka-mop-shop-cart](https://www.notion.so/Users/ceilf6/Desktop/ka-mop-max-duo/packages/ka-mop-shop-cart/src/index.tsx)
- 修改浮层组件本体在 [ka-mop-shop-cart-modify](https://www.notion.so/Users/ceilf6/Desktop/ka-mop-max-duo/packages/ka-mop-shop-cart-modify/src/index.tsx)
- 但“谁去查购物车、谁把 `mopOperateCartVO` / `mopCartItemInfoVO` 传给这些组件、点击修改后 actionType=11/40 怎么发出去”，是在 [food-cart/mop-cart-list/dataSourceMap.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/dataSourceMap.groovy) 和 [food-cart/mop-cart-list/struct.groovy](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/struct.groovy)

再补一个很关键的点：

[food-cart/mop-cart-list/componentsMap.json](https://www.notion.so/Users/ceilf6/Desktop/food-cart/mop-cart-list/componentsMap.json) 里并没有实现组件源码，它只是引用发布后的 npm 组件，比如：

- `@meishi/ka-mop-shop-cart`
- `@meishi/ka-mop-shop-cart-modify`

也就是说 `food-cart` 是“消费组件”的页面协议仓库，不是“实现组件”的仓库。

你之所以会感觉它们又像连在一起，是因为本地联调时，[scripts/food-utils.js](https://www.notion.so/Users/ceilf6/Desktop/ka-mop-max-duo/scripts/food-utils.js) 会把 `ka-mop-max-duo` 里的本地组件代码复制进 `duo-page` 预览页，临时替换掉页面原本依赖的已发布包。

所以开发时看起来像是“页面直接跑本地 packages 代码”，但架构分层上它们还是两件事。

一句话总结：

- 你要看“组件怎么写的” -> 看 `ka-mop-max-duo/packages`
- 你要看“数据怎么来的、怎么传给组件的” -> 看 `food-cart` / `duo-food-order-submit`
- 你要看“最后页面怎么跑起来的” -> 看 `duo-page`
