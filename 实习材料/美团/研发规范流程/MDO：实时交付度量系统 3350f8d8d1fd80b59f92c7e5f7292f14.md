### 1.1.2 公司现状

```
   公司内基本上以质量度量，工时PD和人效数据度量为主：
- 从度量方式上更多停留在传统度量模式下，依赖于以项目管理系统为依托的【人工驱动流程】和【用户主观填报】方式进行数据获取。如下所示：

	- 此种度量模式也会带来以下问题：
		- **数据准确性低**：大量数据依赖手动输入、人工流转，数据准确性受用户主观性影响较大。**填写的数据是否可信？**
		- **维护成本高**：人工输入、人工校准、线下沟通耗时较长……为了维护项目状态准确性，往往需要各职能团队付出大量时间与精力，频繁打断工作进度
		- **数据获取滞后**：历史数据得知，用户操作相对于需求实际进展往往会滞后较多。我们无法更实时、直观的获取到项目真实进展，也不利于管理层及时决策、把握项目风险
- 在度量指标方面更偏向于面向管理导向的指标统计，如工时信息、人效数据，针对效能相关的价值流缺乏有效的指标基准和度量体系支撑。**度量的指标是否合理？**
```

### 1.2 原因分析

```
    我们目前的度量体系更多的是 **面向管理诉求而不是交付价值**，即指标度量的主要目的是为了向管理者们“**证明大家很忙**”，而不是实际产生了哪些价值。《The Principles of Product Development Flow》一书的作者指出：“在产品开发中，问题的关键几乎从来不是停滞的资源，而是停滞的需求”。产品开发的最终目的是交付价值，那我们就必须让价值交付的过程顺畅起来。计划、管理、资源配置等等都应该服务于价值的流动，而不是让资源“**忙起来**”。
                   目前我们更多关注的是资源是否停滞、人是否闲着，但是真正的问题往往是我们平时更难关注到的需求的停滞产生的，比如需求在各个阶段的积压--评审阶段、开发
            阶段、测试阶段、发布阶段等等，而这些才是改进的关键所在。
```

### 1.3 目标

```
   “**让光照亮问题所在**”，想要发现问题必须要让问题暴露在阳光下。我们迫切需要一套更加完善合理的指标模型和度量体系，将“面向管理的**人工流程驱动、用户主观填报**的度量模式”，转变为“**面向用户、面向价值交付**的度量模式”。通过对质量模型的可视化度量、帮助决策者及时发现团队瓶颈和流程中不合理的问题，进而优化流程、协调资源，促进**端到端的价值**在团队内、团队间高效流动。
                   **衡量交付能力，识别交付瓶颈，持续提升交付能力**。实现无需人工填写工时、流转状态，即可客观、实时地度量交付效能。
```

### 2.2 MDO交付模型

结合公司内部的业务实践和业界的交付度量定义，以及质量约束三角形，我们总结了如下的[https://km.sankuai.com/page/417189104](https://km.sankuai.com/page/417189104)：

```
- **交付能力**：
- 	- **吞吐量：**一个研发组织在单位时间内交付的需求数量（需求吞吐量），或一个服务在单位时间内的发布上线频次（服务交付频次）。
	- **高价值交付**：一个研发组织在单位时间内交付高价值需求的能力，需求交付的投入产出比（ROI）。
- **交付效率**：
	- **交付速度**：一个需求或者服务的交付周期。
	- **交付频次：**一个服务在单位时间内的发布上线频次（服务交付频次）。
- **交付质量：**一个需求或者服务在交付到QA后（提测通过）测试发现的缺陷问题数量（线下交付质量），一个需求或者服务在交付到线上（中心发布完成）后发现的缺陷问题数量（线上交付质量）。
- **交付成本**：每个需求/服务的交付成本，可估算为开发人数*交付周期。
```
