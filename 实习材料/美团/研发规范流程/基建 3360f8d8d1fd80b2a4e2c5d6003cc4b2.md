### 5. HTTP 请求链路

#### 5.1 请求封装

应用层封装示例（[`apps/ka-mop-toolkit/src/apis/request.ts`](apps/ka-mop-toolkit/src/apis/request.ts)）：在 shared 的 `getRequest` / `postRequest` 之上统一补充 `epassporttoken`（来自 `authHeaderProvider` / store）。
底层策略摘要（[`shared/library/request.ts`](shared/library/request.ts) 文件头注释）：**Android / iOS 走 MRNUtils 加签；鸿蒙走 MSI**（细节以代码与学城链接为准）。
#### 5.2 请求自动上报

业务通过 `getRequest` / `postRequest` 发请求时，**无需单独写上报**：封装层会按结果自动打 **CAT 指标**（`reportMetics`）和必要时打 **错误日志**（`reportError`）。
上报逻辑：
	- **指标 key**：`params.key`，缺省为 `params.url`（下称 `raptorKey`）。
	- **成功且通过校验**（默认：`res.data` 存在且无 `res.error`）：`reportMetics` 上报 `{ [raptorKey]: 1 }` 以及耗时 `{ [raptorKey]-time: ms }`。
	- **成功但校验失败**（业务结构不符合预期）：`reportError`（`ajaxError`）+ `reportMetics` 中该 key 记 `0`，并带 `errCode` / `errMsg`；可带 `M-TraceId`。
	- **网络/请求失败**（catch / MSI fail）：同上记 `0` + `reportError`（`ajaxError`）。
	- **底层实现**：`reportMetics` → `sendCatLogOwl`；`reportError` → `reportJSInfo`（Owl），并合并系统/页面等公共 tags。
相关文件
	- `request.ts`：统一请求与成功/失败分支里的上报调用。
	- `report.ts`：`reportError`、`reportMetics` 及 Owl/CAT 封装。

### 6. Pike 链路

#### 6.1  定位与依赖

	- **能力来源**：美团 MRN 容器侧通过 **KNB** 暴露的 `pike.initClient`、`pike.startClient`、`pike.releaseClient`。
	- **本模块职责**：将上述桥调用封装为 Promise 式 API，固定「初始化 + 注册下行回调 → 启动」顺序，并对下行 payload 做统一解析后回调业务。
	- **明确不包含**：Global 隧道相关能力（如 `addTunnelStateListener`）、基于隧道状态的自动重连、AggPike 等多连接形态（若后续需要应另起封装）。
#### 6.2 对外接口

| 能力 | 说明 |
| --- | --- |
| ```
createManagedPike(options)
``` | 工厂方法；入参含 `bizId`、`alias`、`onMessage`，可选 `extra`。 |
| 实例 `start()` | 等价于依次执行 `initClient`（含持续回调与 `handle`）与 `startClient`；若已处于已连接状态则直接返回。 |
| 实例 `destroy()` | 等价于 `releaseClient`；销毁后不再触发下行回调，且不可再次 `start`，需重新创建实例。 |
业务侧推荐与页面/容器生命周期绑定：进入时 `start()`，离开时 `destroy()`。
```jsx
export function useOrderPikeChannel(params: UseOrderPikeChannelParams) {
  const { onMessage } = params;
  const { bizUserInfo } = useStore();
  const pikeAliasFromUser = bizUserInfo.extra.uuid.trim()

  useEffect(() => {
    if (!pikeAliasFromUser) {
      return undefined;
    }
    const pike = createManagedPike({
      bizId: ORDER_PIKE_BIZ_ID,
      alias: pikeAliasFromUser,
      onMessage,
    });
    pike.start().catch(() => undefined);
    return () => {
      pike.destroy().catch(() => undefined);
    };
  }, [onMessage, pikeAliasFromUser]);
}
```

### 6.3 链路与时序

**启动**

1. 
    - 校验 `bizId`、`alias`、`onMessage` 及环境是否具备 `KNB.use`。
2. 
    - 调用 `pike.initClient`：传入 `bzId`（与业务 `bizId` 对应）、`alias`、`needContinuousInvoke: true`，以及 `handle`；`extra` 经 `normalizeKnbExtra` 转为键值均为 string 的结构以满足桥约定。
3. 
    - 调用 `pike.startClient` 完成客户端启动。
    该顺序保证在 `startClient` 之前已注册下行处理逻辑，降低消息在「未挂监听」窗口内丢失的风险。
    **下行消息**
    - 桥通过 `initClient` 的 `handle` 将数据回传至封装内部。
    - `dispatchDownstream` 支持单条对象或 `messageList` 数组，统一映射为 `PikeMessagePayload`（含 `bizId`/`messageId`/`content` 等），再调用业务传入的 `onMessage`。
    **销毁**
    - 调用 `pike.releaseClient`，并复位内部状态（`clientInited`、`hasOpened`），置 `destroyed` 以禁止后续回调与重复启动。
    **Promise 封装**
    - `knbPikeUse` 将 KNB 的 `success`/`fail` 转为 Promise，失败时尽量附带 `errno`、`errMsg` 等信息，便于业务侧打点与排查。

```
- cursor 日常代码生成：通过全仓 mdc 文件要求更新对应 mdc 文件
- 全仓巡检：`module-mdc-audit-fix` SKILL  进行全仓巡检
```

### 1. `mdc-update.mdc` （日常准则）

这是**写代码时默认要遵守**的模块文档约定，核心可以记四条：
- **触发**：新建可独立理解的目录单元（新页面、apis 新领域、shared 新的一级子包、较大组件目录等）要**补** `module.mdc`；模块**拆分/合并、对外入口或与其他模块边界变化**时要**改**对应 `module.mdc`。
- **自检**：每次改动看是否落在已有 `module.mdc` 目录树下——职责、对外用法、目录结构变了就更新（或改父级说明）；新增了独立单元就**同步**建文档，不要留「无说明的新模块」。
- **位置**：默认 `<模块根>/.cursor/rules/module.mdc`；单文件能长期代表整块领域时可在**父级** `module.mdc` 用一条说明代替新建；包级总览放在 `ka-mop-toolkit`、`shared` 等包根，子目录只写本模块视角。
- **内容**：只写**作用、边界、维护方式**（必要时链到同目录 `api.mdc`、`request.mdc`）；中文短句列表，**不写**长篇实现与逐函数说明。
细则与原文始终以 `.cursor/rules/mdc-update.mdc` 为准。

### 2. `module-mdc-audit-fix` SKILL 巡检

路径：`.cursor/skills/module-mdc-audit-fix/SKILL.md`。用于**全仓对照**「源码树 / 导出与注册」和已有 `module.mdc`，**只动文档**（`module.mdc` 与报告），不借机改业务代码；文风仍遵循 `mdc-update`。
推荐流程可概括为 **Phase 0～2**：

1. 
    - **划轨（Phase 0）**：按包或分层（基建 / 页面 / 组件等）把目录切成多条**尽量不相交**的巡检线，避免并行改同一文件。
2. 
    - **并行巡检（Phase 1）**：每条轨对照「是否应有说明、现有 `module.mdc` 是否过时或缺失」，用统一状态 `PASS` / `UPDATE` / `MISSING` / `NEW_OPTIONAL` 输出表格行；协调者在 monorepo 根目录合并为 `MODULE_MDC_AUDIT_REPORT.md`（含全局修复优先级与各轨分节）。
3. 
    - **并行修复（Phase 2）**：按报告中每个工作节派修复任务，按「建议动作」新建或修改 `module.mdc`；`NEW_OPTIONAL` 优先在父级 `module.mdc` 加一行，确有独立对外边界再新建文件。

```bash
#!/bin/bash

# 加载 nvm 并切换到 Node 16
if [ -s "$HOME/.nvm/nvm.sh" ]; then
    export NVM_DIR="$HOME/.nvm"
    \\. "$NVM_DIR/nvm.sh"
    \\. "$NVM_DIR/bash_completion" 2>/dev/null || true
    echo "使用 nvm 管理 Node 版本"
    nvm use 16 2>/dev/null || nvm use node 2>/dev/null || echo "警告: 无法切换到 Node 16"
else
    echo "未检测到 nvm，使用系统默认 Node 版本"
fi

# 显示当前 Node 版本
echo "当前 Node 版本: $(node --version 2>/dev/null || echo '未安装')"

# 启动 MCP 服务器
echo "启动 MCP 服务器..."
npx -y @nibfe/max-kb-retrieval-server max-base-components max-api
```
