**Spec Coding** 成为核心思想，它倡导“规范先于生成、验证内嵌流程”，将研发的关注点从代码行转向了交付结果与验收标准。

**Harness Engineering** 则提供了工程化的“缰绳”，通过构建约束、模板和流程，将AI能力驯化为稳定、可控、可复用的生产力

**多Agent协作** 与 **云端执行环境** 等技术方案，共同构成了支撑这一新范式的基础设施

从PRD生成到PR提交的 **端到端AI自驱流程** 如何将需求闭环缩短至2小时；**知识画像驱动的用户仿真** 如何提前暴露体验问题；AI Agent如何成为治理 **技术债务** 的得力助手。这些实践并非孤立的技巧，它们共同指向一个目标：构建一个AI深度融入需求、开发、测试、发布全流程的，**可持续演进的研发闭环体系**

考虑问题规模我认为是对的

- 小仓库比如5000行以内，可能连目录都不需要，每次让AI自己读全文也没啥

### 3.3.1 大模型指令遵循异常

> **ℹ️ 信息：**
> 
> 
> **问题详述**：在长链路任务执行过程中，大模型存在偏离预设流程的风险，具体表现包括：跳过关键业务校验步骤、工具调用时序错乱、流程分支判断失误等。此类场景大多是因为随着 Spec 流程的推进，上下文信息量快速累积，容易导致大模型出现历史信息检索失效与幻觉输出等问题。
> 
> **解决策略**：多智能体协作设计
> 

### 多智能体设计

通过 multi-agents 架构避免单个 agent 加载超长上下文，通过职责单一化减少大模型的判断负担，提升指令遵循的稳定性。

**（1）单智能体任务简化：包括步骤逻辑简化**、**大模型职责范围缩小**；例如：精简冗余指令，将复杂的多步骤判断拆解为单一明确的任务目标，也能减轻大模型的幻觉问题；同时设计**工具抽离**策略**，**将流程控制、基建打通等确定性逻辑从大模型中剥离，交由专门的工具模块处理。大模型仅负责核心的内容生成工作，避免承担过多判断职责。

**（2）协作执行链路：**

- *文档驱动的统一调度架构：**通过 SpecMasterAgent 统一调度多个专业 Agent，所有 Agent 通过读写 .codezy 目录下的结构化文档进行信息传递和状态同步，避免 agents 间提示词高耦合度。每个 Agent 职责单一、可独立优化，文档作为契约保证流程的可追溯性和可恢复性。
- *渐进式确认机制：**在需求和设计阶段通过 progress 文件记录迭代过程，支持用户在关键节点介入反馈，确保需求理解和技术方案的准确性。
- *步骤流转解耦：**主 step [^主 step ：准备阶段、需求确认阶段、技术方案设计阶段等]进度通过 .codezy/progress.md 进行管理，specMasterAgent 负责存和读，并指导和分配给其他 subAgents，subAgents 无需关注；子 step [^子 step ：每个主 step 下可能包含多个子 step，例如“需求确认阶段”就包含“初始需求收集”、“需求质量检查”、“根据用户回答问题再次调整需求文档”等]进度需要各 subAgent 自行管理进度，只有当 subAgent 明确表示当前阶段结束后，specMasterAgent 才会进入下一阶段。

> 🔗 **嵌入内容**

**（3）agents 间通信设计：**

- *主子 Agent 通信：**masterAgent 和 subAgents 之间通过出入参设计[^出入参设计：Catpaw Subagent 通信设计]进行通信，并标准化输入输出。
- *子 Agent 间通信：**通过创建和读取 <span style="color:inherit">.codezy/memory/xxx.md</span> 本地文件进行通信，解决 subAgent 上下文割裂问题。

### 3.3.3 大模型重复实现项目中已有的公共方法和变量

> **ℹ️ 信息：**
> 
> 
> **问题详述**：在代码生成过程中，由于上下文检索机制在召回项目相关代码时存在遗漏，导致已封装的工具函数、公共组件和常量定义未能有效纳入上下文。大模型在信息不完整的情况下，往往会重新实现相似功能，造成代码冗余，并可能引入行为不一致的风险，增加后期维护成本。
> 
> **解决策略**：项目架构分析 - 自动提取并纳入上下文中的公共方法/变量
>
