# 技术方案

技术方案先定这几个默认假设：

1. 消费者以智能体为主，人类是辅助使用者。
2. 每个目录维护一个 `FILES.json`，负责“局部环境感知”。
3. 采用“两层模型”：
- 机器索引层：稳定、可增量同步、低歧义。
- 语义描述层：帮助智能体快速理解目录职责、入口文件、约束。
1. `sync` 默认递归处理当前目录及全部子目录，并支持 `.filesignore` / 配置排除。
2. 目标不是替代 git，而是给智能体提供比“扫全量文件树”更便宜、更结构化的环境上下文。

建议方案

一、核心设计

每个目录一个 `FILES.json`，只描述“本目录直接子项”，不跨层展开。
这样有几个好处：

- 局部读取成本低，智能体进入某目录时只需读一个文件。
- 更新简单，目录移动或局部变更只影响局部索引。
- 递归遍历时可按需逐层展开，而不是一次加载全仓库清单。

目录树示意：

`repo/
  FILES.json
  src/
    FILES.json
    components/
      FILES.json
  docs/
    FILES.json`

二、FILES.json 数据模型

建议字段分成 4 组：

1. 元信息
- `schema_version`
- `generated_at`
- `root_relative_path`
- `sync_mode`
- `generator`
1. 目录语义
- `directory_purpose`: 该目录做什么
- `agent_hints`: 智能体注意事项
- `conventions`: 命名/分层/禁止事项
- `key_entrypoints`: 重要入口文件或子目录
1. 子项索引
- `children`: 仅列当前目录直接子文件/子目录
每项建议包含：
- `name`
- `type`: `file` | `dir`
- `path`
- `ext`
- `size`
- `mtime`
- `hash`
- `summary`
- `tags`
- `importance`
- `status`: `active` | `generated` | `deprecated` | `ignored`
1. 同步状态
- `sync`: 最近一次扫描统计
- `issues`: 读不到/损坏/权限问题
- `drift`: 语义摘要是否过期

示例：

`{

  "schema_version": "1.0",

  "generated_at": "2026-05-18T16:05:00+08:00",

  "root_relative_path": "src/components",

  "directory_purpose": "复用 UI 组件目录，优先放无业务耦合组件。",

  "agent_hints": [

    "新增组件前先检查是否已存在同类组件",

    "避免在此目录引入页面级状态管理"

  ],

  "conventions": [

    "文件名使用 PascalCase",

    "样式与组件同目录放置"

  ],

  "key_entrypoints": ["Button.tsx", "Modal.tsx"],

  "children": [

    {

      "name": "Button.tsx",

      "type": "file",

      "path": "src/components/Button.tsx",

      "ext": ".tsx",

      "size": 4210,

      "mtime": "2026-05-18T15:20:11+08:00",

      "hash": "sha1:abc123",

      "summary": "通用按钮组件，支持 primary/secondary/danger 三种视觉变体。",

      "tags": ["react", "ui", "shared"],

      "importance": "high",

      "status": "active"

    }

  ],

  "sync": {

    "child_count": 12,

    "file_count": 10,

    "dir_count": 2,

    "last_full_sync": "2026-05-18T16:05:00+08:00"

  },

  "issues": [],

  "drift": {

    "semantic_fields_stale": false

  }

}`

三、为什么不建议“纯 FILES.json 快照”

如果只有文件名、mtime、hash，这只是更易读的 `find` 结果，对智能体帮助有限。
智能体真正缺的是：

- 这个目录是干什么的
- 哪些文件最重要
- 哪些是生成物，哪些不能改
- 从哪里进入理解代码

所以建议把“硬元数据”和“软语义”分开：

- 硬元数据由 `sync` 自动维护。
- 软语义允许人工补充，或由单独命令生成/更新。

四、CLI 命令设计

建议最小可用命令集：

1. `files init`
作用：
- 在项目根生成配置文件，如 `.filesrc.json`
- 初始化首批 `FILES.json`
1. `files sync [path]`
作用：
- 递归扫描目标路径
- 为每个目录生成/更新 `FILES.json`
- 增量更新 hash/mtime/size/children
- 保留人工维护字段

关键行为：

- 幂等
- 默认递归
- 支持 `-full`、`-changed-only`
- 支持 `-json` 输出变更摘要
1. `files summarize [path]`
作用：
- 为目录或文件补充/刷新 `summary`、`directory_purpose`、`agent_hints`
- 可接 LLM，也可先做规则版
1. `files check [path]`
作用：
- 检查索引漂移
- 检查缺失的 `FILES.json`
- 检查语义字段陈旧度
1. `files query <path>`
作用：
- 给智能体/人类快速取某目录上下文
- 输出精简模式，不必直接读原始 JSON
1. `files prune`
作用：
- 清理已删除目录残留索引
- 修复无效引用

五、sync 设计重点

`sync` 必须把“自动字段”和“人工字段”分离，否则每次同步都会把人工语义覆盖掉。

建议机制：

- 自动区：`children`、`sync`、`generated_at`
- 半自动区：`summary` 可带 `source: auto|manual`
- 人工区：`directory_purpose`、`agent_hints`、`conventions`

同步时：

- 自动区全量重算或增量更新
- 人工区默认保留
- 半自动区仅在 `-refresh-summary` 时改写

可再细一点，采用：

- `FILES.json`：机器维护主文件
- `FILES.notes.json`：人工补充语义
然后读时 merge

如果你强调稳定性，我更推荐“双文件方案”，因为它能彻底避免人工注释被覆盖。

六、推荐的最终落地结构

我建议不要只用一个 `FILES.json`，而是：

- `FILES.json`：机器索引
- `FILES.notes.json`：人工/智能体补充语义
- `.filesrc.json`：全局配置
- `.filesignore`：排除规则

理由：

- 机器同步和语义维护职责分离
- diff 更干净
- 冲突更少
- 后续更容易接不同 summarizer

七、配置文件建议

`.filesrc.json` 示例：

`{

  "schema_version": "1.0",

  "root": ".",

  "recursive": true,

  "index_file": "FILES.json",

  "notes_file": "FILES.notes.json",

  "ignore_file": ".filesignore",

  "exclude": [

    ".git",

    "node_modules",

    "dist",

    "build",

    ".next",

    "coverage"

  ],

  "hash_algorithm": "sha1",

  "summary": {

    "enabled": true,

    "max_file_size_kb": 256,

    "mode": "hybrid"

  }

}`

八、智能体消费方式

智能体读取目录时，约定流程可以是：

1. 先读当前目录 `FILES.json`
2. 如存在 `FILES.notes.json`，合并语义信息
3. 根据 `key_entrypoints` 和 `importance=high` 决定下一步读哪些文件
4. 只在需要时下钻到子目录的 `FILES.json`

这比“从根目录开始全量 ls + rg”更便宜，也更像分层上下文加载。

九、增量同步策略

建议用“mtime + size 快速判断，hash 兜底”：

- 默认先比 `mtime` 和 `size`
- 变化了再重算 hash
- `-full` 时强制全量 hash

原因：

- 纯 hash 太慢
- 纯 mtime 有误判风险
- 混合模式更适合大仓库

十、实现栈建议

如果你要尽快落地，我建议：

- 语言：TypeScript / Node.js
- CLI：`commander` 或 `oclif`
- 文件遍历：`fast-glob` 或原生 `fs/promises`
- hash：Node `crypto`
- JSON schema 校验：`zod` 或 `ajv`

如果你更看重分发简单，也可以用 Go。
但第一版为了 LLM 集成、JSON 操作、生态速度，我更推荐 TypeScript。

十一、版本路线

Phase 1：可用

- `init`
- `sync`
- `check`
- `.filesignore`
- 每目录一个 `FILES.json`

Phase 2：智能体增强

- `FILES.notes.json`
- `summarize`
- `query`
- `importance` / `tags` / `entrypoints`

Phase 3：持续性

- git hook: `post-merge` / `pre-commit`
- watch 模式
- CI 校验 drift
- 与 IDE/agent runtime 集成

十二、关键风险

1. 语义摘要容易过期
解决：
- 把摘要和索引分层
- 增加 `drift` 标志
- 用 `check` 检测
1. 大仓库同步慢
解决：
- 增量扫描
- ignore 规则
- mtime+size+hash 混合判断
1. 人工修改被覆盖
解决：
- 双文件方案
- 或字段级保护
1. JSON 过大影响读取
解决：
- 每目录仅记录直接子项
- 不在根目录塞全量树

结论

推荐你直接做成“分层目录索引系统”而不是单纯的文件快照系统：

- 每个目录一个 `FILES.json`，只记录直接子项的机器索引。
- 每个目录可选一个 `FILES.notes.json`，记录面向智能体的语义说明。
- `sync` 递归、幂等、增量更新，保留人工语义。
- 智能体按目录逐层加载，而不是一次性扫描整个仓库。

这是我认为当前最适合智能体的方向：成本低、结构稳定、可持续维护，也方便后续接 LLM 摘要、IDE 插件、RAG 或 agent runtime。
