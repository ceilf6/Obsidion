# Graph 和 State

把 LangGraph 理解成一个**“用图来编排 LLM / Agent 工作流的底层框架”**会比较容易：它把复杂的 AI 应用拆成一组节点和边，节点负责处理，边负责决定下一步怎么走；整个过程中，所有节点共享一份可演进的状态。官方把它定位为一个用于构建**长运行、可控、带状态的 agent** 的低层编排框架。

下面我按“先建立直觉，再讲术语”的方式介绍。

## **1. LangGraph 是什么**

如果你之前只写过“单次 prompt -> 模型输出”，那 LangGraph 解决的是更复杂的场景：

- 需要多步推理
- 需要调用工具
- 需要失败后恢复
- 需要人工介入审批
- 需要长期记忆或会话状态
- 需要分支、循环、并行执行

官方文档里，LangGraph 的核心价值集中在几件事：**agent orchestration（代理编排）**、**stateful execution（有状态执行）**、**human-in-the-loop（人类介入）**、**persistence / checkpoints（持久化与检查点）**。

你可以把它和 LangChain 的关系理解为：

- **LangChain** 更偏“组件和集成层”，方便你接模型、工具、检索器
- **LangGraph** 更偏“流程控制层”，负责把这些能力编排成可靠的执行图

而且官方明确提到，LangChain 里的某些 agent 能力本身就是构建在 LangGraph 之上的。

---

## **2. 最核心的思维模型：Graph + State**

LangGraph 最重要的两个词其实就两个：

### **Graph**

图，就是一张流程图。

它由这些东西组成：

- **Node（节点）**：一步处理逻辑
- **Edge（边）**：从一个节点流向另一个节点的连接
- **Start / End**：开始和结束位置
- **Conditional routing**：根据条件决定走哪条边
- **Loop**：需要时可以回到前面继续执行

官方在 Graph API 文档中明确把常见结构归纳为：**sequences（串行）**、**branches（分支）**、**loops（循环）**。

### **State**

状态，就是这张图运行过程中共享的数据。

LangGraph 的一个关键特点是：**节点不是互相直接传参，而是通过共享状态来通信**。在 LangGraph.js 的 StateGraph 说明中，官方写得很清楚：节点读取一个定义好的 State，并返回一个 Partial<State>；多个节点的更新可以通过 reducer 聚合。

所以它不是“函数 A 的返回值直接传给函数 B”，而更像：

1. 节点 A 读取当前 state
2. 节点 A 返回对 state 的增量更新
3. 框架把更新合并回 state
4. 下一个节点继续读取新的 state

这个设计特别适合 agent，因为 agent 往往需要反复累积：

- 用户输入
- 中间推理结果
- 工具调用结果
- 审批意见
- 历史消息
- 错误信息
- 下一步计划

---

## **3. StateGraph：LangGraph 的核心抽象**

官方把 StateGraph 定义为：**一个节点通过读写共享状态来通信的图**。每个节点输入 State，输出 Partial；每个 state 字段还可以指定 reducer，用来合并来自多个节点的更新。

这意味着 StateGraph 是你最常用的图类型。它背后的思想是：

- 把应用的数据结构先定义清楚
- 再把每一步逻辑作为节点挂到图上
- 用边定义执行路径
- 由框架负责状态合并和调度

这和传统“写一大串 if/else + while + try/except”相比，更适合维护复杂 agent 工作流。

---

## **4. 节点（Node）**

节点可以理解为一段业务逻辑。

典型节点可能做这些事情：

- 调用大模型生成回复
- 判断是否需要调用工具
- 执行检索
- 整理工具结果
- 做安全审查
- 等待人工批准
- 决定是否结束

从概念上说，一个节点的输入是当前 state，输出是对 state 的更新。

### **节点的特点**

第一，它通常应该**只做一步清晰的事**。

第二，它尽量**无副作用或副作用可控**。

第三，它最好把输出写回 state，而不是偷偷依赖外部隐式变量。

### **一个很实用的理解**

你可以把节点想成“工作流中的一个工位”。

每个工位拿到同一张工单（state），处理后在工单上补几项内容，再把工单交给下一个工位。

---

## **5. 边（Edge）**

边定义了“下一步去哪”。

LangGraph 中常见有两类：

### **普通边**

就是固定跳转。

例如：

解析输入 -> 检索资料 -> 生成回答 -> 结束

### **条件边**

根据 state 中的信息动态决定跳转路径。

例如：

- 如果模型说需要工具，就去 tool_node
- 如果已经有最终答案，就去 END
- 如果结果不满意，就回到 plan_node 重新规划

官方文档把分支和循环视为 Graph API 的基础结构之一。

这也是 LangGraph 比“线性链式调用”强很多的地方：

它天然适合**决策型流程**，而不仅仅是顺序执行。

---

## **6. Reducer：为什么状态合并很重要**

这是 LangGraph 初学者常忽略，但实际上非常关键的概念。

因为在图执行中，尤其在**并行分支**或**多节点都更新同一字段**时，框架必须知道：

> “两个更新同时写到同一个 state key，怎么合并？”
> 

这时就用 **reducer**。

官方说明里说得很明确：每个 state key 都可以带一个 reducer，签名类似 (left, right) => value，用于聚合多个节点写入的值。

### **举例**

如果 state 里有个 messages 字段：

- 节点 A 追加一条消息
- 节点 B 也追加一条消息

那 reducer 可能就是“把两个列表拼接起来”。

如果没有 reducer，系统就不知道该覆盖谁。

所以 reducer 的本质是：**定义并发或多来源更新时的合并规则**。

---

## **7. Compile（编译）是什么意思**

在 LangGraph 里，图搭好后不能直接跑，通常要先 **compile**。

官方文档解释得很清楚：编译并不神秘，主要是做几件事：

- 检查图结构是否合理
- 检查是否有孤立节点等结构问题
- 注入运行时参数
- 配置 checkpointer、breakpoints 等能力

而且官方明确说：**graph 必须 compile 后才能使用**。

所以“编译”在这里不是传统意义上的机器码编译，更像：

> 把你声明式定义的流程图，变成一个可运行的执行对象。
> 

---

## **8. Persistence / Checkpointer / Checkpoint**

这是 LangGraph 非常有代表性的能力。

官方文档指出，LangGraph 内建持久化层，会把图的状态保存为 **checkpoints**；如果你在编译时配置了 checkpointer，系统会在每一步执行时保存状态快照，并按 **threads** 组织。这样就支持：

- human-in-the-loop
- conversational memory
- time travel debugging
- fault-tolerant execution

这些都是官方原文强调的用途。

### **这些词分别是什么意思**

### **Checkpoint**

某一步执行后的状态快照。

### **Checkpointer**

负责把 checkpoint 存起来的机制或组件。

### **Persistence**

整个持久化能力，也就是状态不会只存在内存里，而能被恢复。

### **为什么重要**

普通脚本如果运行到一半崩了，可能要从头再来。

但 LangGraph 有 checkpoint 后，可以从某个保存点恢复，而不是完全重跑。

这对于长任务、昂贵任务、涉及人工审批的任务尤其关键。

---

## **9. Thread：线程不是操作系统线程**

LangGraph 文档里的 **thread**，更接近“某次会话 / 某条执行轨迹的身份标识”。

官方在持久化说明中说，checkpoint 是按 threads 组织的。

你可以把 thread 理解为：

- 一个用户会话
- 一个任务实例
- 一条可恢复的执行历史

这样同一个图可以服务很多次运行，而每次运行各自有不同的状态历史。

---

## **10. Interrupt：中断与 Human-in-the-loop**

这是 LangGraph 很强的一块。

官方文档里说，**interrupts 允许你在图执行的特定点暂停，并等待外部输入后再继续**。当 interrupt 触发时，LangGraph 会通过持久化层保存状态，之后可以无限期等待恢复。

这意味着你可以很自然地做这些流程：

- “模型准备发邮件，但先给人审批”
- “高风险操作前先人工确认”
- “补充缺失资料后再继续”
- “人工修改模型草稿，然后恢复执行”

### **一个直观例子**

1. 节点生成合同摘要
2. 节点触发 interrupt
3. 人工在界面上看摘要并点“通过”
4. 图从中断点恢复
5. 继续发送给客户

这个模式就是典型的 **human-in-the-loop**。官方也把它作为 LangGraph 的核心能力之一。

---

## **11. Send API：并行 / Map-Reduce**

Graph API 文档提到，LangGraph 提供 **Send API** 来支持 **map-reduce workflows**。

这通常用于：

- 把一个大任务拆成多个子任务并行跑
- 然后把多个子结果聚合回来

### **典型场景**

比如你有 20 份文档要总结：

- map 阶段：把 20 份文档分别发给多个节点处理
- reduce 阶段：把 20 个摘要聚合成一个总摘要

这时 reducer 往往也很关键，因为最终需要把多个结果写回 state 并合并。

---

## **12. Command API：更新状态 + 控制跳转**

官方 Graph API 文档中还提到 **Command API**，用于把**状态更新**和**跨节点跳转（hops）**结合在一起。

这个概念的价值在于：

有时一个节点不仅想返回“数据更新”，还想顺便说：

> “并且下一步请直接去某个指定节点。”
> 

也就是说，节点既影响数据，又影响控制流。

你可以把它理解成一种更强的返回值，不只是“我算出了什么”，还包含“接下来去哪”。

---

## **13. Loop：为什么 LangGraph 特别适合 Agent**

很多 agent 不是一步出答案，而是下面这种循环：

1. 先规划
2. 看是否缺信息
3. 需要就调用工具
4. 读工具结果
5. 重新规划
6. 直到满足结束条件

这种模式本质上就是一个图里的循环。官方也把 loop 作为图 API 的基础结构来介绍。

所以你会看到 LangGraph 很适合实现常见 agent 模式：

- ReAct 风格的思考-行动循环
- Planner-Executor
- 多 agent 协作
- 工具调用闭环
- 带审查的执行链

---

## **14. Memory：LangGraph 里的“记忆”到底是什么**

很多人会把“memory”理解成聊天历史，其实在 LangGraph 里它更广。

根据官方持久化文档，持久化和 checkpoint 支持 conversational memory；同时官方 README 也强调了 long-term memory 能力。

你可以把 memory 分成两层理解：

### **运行期状态记忆**

也就是当前 thread 的 state，一步步累积。

### **跨会话长期记忆**

把某些信息保存下来，下一次运行还能继续使用。

LangGraph 本身更像是提供“状态与持久化的基础设施”；至于长期记忆具体存什么、怎么召回，通常还会结合数据库、向量库或其他存储策略。

---

## **15. 子图（Subgraph）与模块化**

虽然你问的是基本概念，但这个也很值得提前知道。

当图变复杂后，你不会想把所有节点都堆在一层。实践里通常会把一部分流程封装成**子图**，例如：

- 一个“检索问答子图”
- 一个“工具执行子图”
- 一个“审批子图”

这样做的意义是：

- 结构清晰
- 便于复用
- 更接近工程化模块设计

虽然这不是你入门时第一天必须掌握的 API 细节，但从概念上，LangGraph 很适合这样做，因为它本来就是图式编排框架。这个模块化方向也和官方对复杂 agent orchestration 的定位一致。

---

## **16. 一个最小执行模型：你可以这样理解 LangGraph 的运行过程**

把它压缩成一句话：

> **定义状态 -> 定义节点 -> 定义边 -> 编译 -> 运行 -> 每步更新状态 -> 必要时持久化 / 中断 / 恢复 -> 到达结束节点**
> 

这套流程和官方 Graph API overview、Persistence、Interrupts 文档是一致的。

---

## **17. LangGraph 和普通工作流引擎的区别**

它不是一个通用 BPM 系统，也不只是“画流程图”。它更偏 AI/Agent 场景，特点在于：

- 把 **LLM 调用** 当作一等公民
- 把 **共享状态** 作为核心抽象
- 内建 **checkpoint / persistence**
- 强调 **human-in-the-loop**
- 适合 **长运行** 和 **可恢复** 的 agent

这些特征都来自官方对其定位和能力说明。

---

## **18. 初学者最容易混淆的几点**

### **LangGraph 不是“替代 LangChain 的全部”**

更准确地说，它更像**编排层**，而 LangChain 偏**组件层**。两者经常一起使用。

### **State 不是普通临时变量**

它是整个图的共享数据模型，是节点之间沟通的核心媒介。

### **Compile 不是性能优化步骤**

它首先是**把图变成可运行对象并做结构检查**。

### **Interrupt 不只是“暂停”**

它通常和**持久化恢复**、**人工输入**绑定在一起。

### **Memory 不只是聊天记录**

它还包括 checkpoint、thread 上下文，以及更广义的长期记忆体系。

你可以按下面这个顺序掌握 LangGraph：

**第一层：图结构**

- Node
- Edge
- Conditional Edge
- Loop

**第二层：状态模型**

- State
- Partial State Update
- Reducer
- StateGraph

**第三层：运行控制**

- Compile
- Command
- Send
- Streaming

**第四层：可靠性**

- Checkpoint
- Checkpointer
- Persistence
- Thread
- Resume / Recovery

**第五层：人机协作**

- Interrupt
- Human-in-the-loop

这基本覆盖了 LangGraph 的核心世界观。相关概念都能在官方 Graph API、StateGraph、Persistence、Interrupts 文档中找到对应依据。
