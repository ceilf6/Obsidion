# 统一鉴权

统一鉴权 = 统一配置解析 + 统一核心鉴权函数 + 各传输层只做凭证提取与少量场景差异

将所有入口先归一城同一个鉴权模型，再交给同一个核心函数判断

将配置、环境变量、CLI覆盖项解析成一个统一格式的鉴权配置实例，再交给网关服务启动

这里还做了一层安全兜底：如果不是 loopback 绑定，又没有共享密钥鉴权，就拒绝启动；trusted-proxy 是例外

```tsx
export function resolveGatewayAuth(params: {
  authConfig?: GatewayAuthConfig | null;
  authOverride?: GatewayAuthConfig | null;
  env?: NodeJS.ProcessEnv;
  tailscaleMode?: GatewayTailscaleMode;
}): ResolvedGatewayAuth { }
```

判断是否放行：

```tsx
export async function authorizeGatewayConnect(
  params: AuthorizeGatewayConnectParams,
```

共享代理模式 trusted-proxy 先校验来源 **IP 是否在 trustedProxies 中**，再**从指定 header 里取用户身份**；

none 直接放行；

其余模式进入统一的共享密钥校验流程，支持限流；

WS Control UI 场景下，还允许 Tailscale 头部鉴权；

最后再比较 token 或 password。

应用层协议 http 和 WebSocket 都只是薄封装，共用的是同一个鉴权内核，但它们进入内核前后的处理并不一样

1. 凭证放在哪里不一样
    
    HTTP 走请求头。标准网关鉴权 helper 只从 **请求头Authorization**: Bearer 里取 token，然后把它同时映射成 token 和 password 两个候选字段，再交给统一鉴权函数：
    
    WebSocket 不走请求头里的 Bearer 作为主入口，而是客户端在第一次 connect 帧里显式带 **auth 对象**，里面可以有 token、password、deviceToken：
    
    所以 HTTP 更像“**单次请求带一个 Bearer**”；WebSocket 更像“**连接建立时提交一份结构化认证材料**”。
    
2. HTTP 只有共享密钥入口，WS 额外支持 device token
    
    HTTP 进入统一鉴权时，传入的 connectAuth 只有 token 或 password 这类共享密钥候选，没有 deviceToken 这条分支：
    
    WS 握手阶段会先做共享密钥鉴权，然后如果客户端带了设备身份，还会继续尝试 device token 这条链路。也就是说，WS 有两层决策：
    先判断共享密钥或 trusted-proxy 是否通过；
    如果没通过，但带了设备身份和 device token，还可以继续走设备鉴权。
    
    这就是最核心的不同点之一：**HTTP 只有“请求级共享密钥鉴权”，WS 还有“连接级设备鉴权”**。
    
3. Tailscale 透传鉴权的开关不一样
    
    auth.ts 里写得很直接：HTTP surface 明确禁用 Tailscale forwarded-header auth；WS Control UI 则故意允许它，用于 tokenless trusted-host login：
    
    具体实现上，统一鉴权函数里只有当 authSurface 允许时，才会走这段 Tailscale 用户识别逻辑：
    auth.ts
    
    所以 HTTP 和 WS 并不是只差“从哪取 token”，还差“**是否允许某些无 token 的可信网络登录**方式”。
    
4. **WS 在鉴权前还有一层协议和浏览器安全检查**，HTTP 没这层握手语义
    
    WS 在 connect **握手里先校验协议版本是否兼容**，不兼容直接拒绝连接：
    message-handler.ts
    
    如果是 Control UI 或浏览器来源，还会做 Origin 校验，避免任意网页跨站连进来：
    message-handler.ts
    
    HTTP 这边没有“连接握手”和“协议版本协商”这类概念，通常就是每个请求直接进 Bearer 校验：
    http-endpoint-helpers.ts
    
5. WS 的鉴权结果会影响后续角色、配对和 scope；HTTP 基本只决定这次请求放不放行
    
    WS 握手成功后，authResult、authMethod、sharedAuthOk 会继续参与后面的控制逻辑，比如：
    是否允许没有 device identity 的 Control UI 接入；
    是否清空未经绑定的 scopes；
    是否跳过 pairing；
    是否允许 trusted-proxy operator 直接通过。
    这些都发生在握手成功后的连接建立阶段：
    
    HTTP 一般没有这套“连接建立后继续绑定设备/角色上下文”的流程。它更偏向“本次请求是否授权”。
    
6. 限流粒度也不完全一样
    
    HTTP 基本就是共享密钥失败按请求来源 IP 计数。
    
    WS 则拆成了至少两类限流：
    共享密钥限流；
    device token 限流。
    而且浏览器来源还会切到更严格的 browserRateLimiter，loopback 也不豁免：
    
    可以把两者概括成一句话：
    
    **HTTP 是“每个请求做一次共享密钥鉴权”；**
    **WS 是“先做握手鉴权，再把鉴权结果继续用于**设备身份、配对、角色和会话级**授权**”。
