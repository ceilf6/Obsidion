# TDD vs SDD

**TDD** 通常指 **Test-Driven Development，测试驱动开发**。

它的核心流程是：

1. 先写一个失败的测试
2. 写最少的代码让测试通过
3. 重构代码
4. 重复以上过程

也就是常说的：

**Red → Green → Refactor**

例子：

```python
def test_add():
    assert add(1, 2) == 3
```

先写测试，再实现：

```python
def add(a, b):
    return a + b
```

---

**SDD** 这个缩写有几种含义，最常见的是 **Specification-Driven Development，规格/规范驱动开发**，也有人用它指 **Software Design Document，软件设计文档**。

如果你问的是开发方法论里的 SDD，一般指 **规格驱动开发**。

它的核心是：

先明确系统应该满足什么规格、接口、行为、约束，再根据规格实现代码。

---

## TDD 和 SDD 的区别

| 对比项 | TDD | SDD |
| --- | --- | --- |
| 驱动来源 | 测试用例 | 规格说明 / 设计文档 / 接口规范 |
| 关注点 | 代码行为是否正确 | 系统应该做什么、怎么设计 |
| 开始时做什么 | 先写测试 | 先写规范或设计 |
| 更偏向 | 实现层、代码层 | 需求层、设计层、接口层 |
| 典型产物 | 单元测试、集成测试 | PRD、接口文档、设计文档、协议规范 |
| 适合场景 | 逻辑明确、可测试的功能开发 | 系统设计、API 设计、多人协作、大型项目 |

---

简单理解：

**TDD 是“用测试来驱动代码怎么写”。**

**SDD 是“用规格/设计来驱动系统怎么做”。**

实际项目里二者可以结合：

先用 **SDD** 定义清楚需求、接口和架构，再用 **TDD** 保证每个功能按预期实现。
